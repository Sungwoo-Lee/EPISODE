Recurrent PPO · return computation

Two Currencies, One Sum

A number measured on one scale is being added to numbers measured on a completely different scale. Everything else in this document follows from that one fact.

Two things are easy to conflate here, so stated up front: chopping training into fixed windows is standard practice and is not the problem — every reinforcement-learning library does it, and the technique for handling the resulting edge is settled (§2). The defect is something this codebase does in addition: it rescales the returns before using them (§3 onward).

Read this before acting on the recommendation below

The repair this document argues for was built, run, and lost badly. Five seeds per arm on the 10×10 world, one million episodes each: the agent trained the current (allegedly broken) way survived 138.2 steps on average, while the repaired arm managed 40.3 and the clean GAE arm 41.9. The diagnosis in §1–§7 is unchanged and still correct as a description of the code — the units really are mismatched. What is wrong is the conclusion that fixing it in isolation would help. §10 has the result and the reason.

Written for someone meeting this for the first time. Every term is defined where it first appears, and there is a glossary at the end.

1. What the trainer is trying to compute

After the agent acts for a while, the trainer looks back and computes two things for every step: a return and an advantage. Both are worth seeing on a real episode before anything goes wrong.

Computing the return

↓ general form in Appendix A.1

The return at a step is everything that followed it, with each later reward counted slightly less — 95% per step here. You can only compute it once you know how things ended, so you start at the last step and walk backwards:

return(step) = reward(step) + 0.95 × return(next step)

The episode ends at step 13, so nothing follows it and its return is just its own reward:

step 13:  −128.62  // nothing follows — the episode is over
step 12:  −21.56 + 0.95 × (−128.62) = −143.75
step 11:  −21.29 + 0.95 × (−143.75) = −157.85
step 10:   −0.30 + 0.95 × (−157.85) = −150.25
  … continuing back …
step  1:    0.00 + 0.95 × (−66.90) =  −63.56

What the return is actually saying

Step 1's reward was 0.00, and the next eight steps were all positive — the agent was healing nicely. Yet step 1's return is −63.56.

Breaking that number apart: the nine healing steps contribute +31.14, the two attacks contribute −25.20, and the single death step contributes −69.50 — because 0.9512 is still 0.54, so a death twelve steps away arrives at over half strength.

That is the whole point of a return. It is not "how good did that step feel"; it is "where did that step lead". Nine steps of genuine progress are wiped out by one death twelve steps later, and the return says so.

Computing the advantage

↓ general form, and the TD error, in Appendix A.3

The return alone cannot train a policy, because it does not say whether the outcome was surprising. A return of −63.56 means one thing if the agent expected disaster and something else entirely if it expected to be fine.

That is what the critic is for: it predicts the return from each state. The advantage is the gap between what happened and what the critic expected:

advantage = return − critic's prediction

The recorded trajectory files do not store the critic's predictions, so the two numbers below are illustrative — the returns are real, the predictions are not.

StepReturn (real)Critic expectedAdvantageWhat the policy learns
1−63.56−20.00−43.56far worse than expected — make these choices less likely
9−138.14−140.00+1.86about as expected — barely change anything

Sign is what matters. A positive advantage pushes the policy to repeat what it did; a negative one pushes it away. Notice step 9 has a far worse return than step 1 but a mildly positive advantage — by then disaster was already unavoidable and the critic knew it, so there is little to learn. The return says what happened; the advantage says what was worth learning from.

When this happens

Not during play. The agent acts for a fixed stretch, and only afterwards does the trainer walk backwards over what it collected. With this project's live settings, one cycle looks like this:

PhaseWhat happensScale
1. Collect128 environments run in parallel for 128 steps each. Rewards are recorded. No return exists yet — nothing can be computed until the stretch is over.16,384 steps
2. ComputeWalk backwards through each environment's own column of 128 steps, building returns, then advantages.128 passes
3. LearnFour passes of gradient updates over those 16,384 samples.4 epochs
4. DiscardThe data is thrown away and collection starts again — PPO learns only from experience its current policy just produced.—

Each of those 128 columns has its own stopping point. So every iteration creates 128 edges — one per environment — and each one needs a number standing in for the future beyond it.

How often does an edge land mid-episode?

Almost always. Measured over 5,000 real episodes: mean length 195 steps, median 84, and an episode ends exactly on a 128-step boundary 0.18% of the time.

So the situation section 4 describes — a window stopping in the middle of an ongoing episode — is not an edge case. It is essentially every edge, every iteration.

Over the planned 10M-episode budget that is roughly 1.95 billion environment steps, 119,000 training iterations, and about 15 million window edges — each one seeded with a number in the wrong units.

That stretch is the window, where it stops is the edge, and the number standing in for what lies past it is the starting value. Those three terms carry the rest of the document — so it is worth seeing, in numbers, how much that third one decides.

Why a starting value is needed at all

Here is the tension in one sentence. The return is defined by accumulating backwards from the end of the episode — but the trainer only ever holds a 128-step slice, so it has to start accumulating from the end of the slice instead. Something has to stand in for the part it cannot see.

The exact statement of the problem

Look at the middle column. Given the right starting value, the windowed computation reproduces the true returns exactly — 6.513, 6.126, 5.695, all of them. Cutting the episode into windows costs nothing at all, provided the right number is inserted at the cut.

So the entire problem reduces to one question: what number goes at the edge? Everything else — the recursion, the discounting, the windowing — is exact.

And the last column shows what a wrong one costs. The shortfall is 0.9distance × 4.095: largest at step 5, right against the edge, fading as you move back. Which is exactly the pattern seen later on real data, and for exactly this reason.

One thing this toy case makes obvious that the real one hides: the trainer is not being careless. Steps 6–10 have not been collected yet when the returns are computed. The number at the edge cannot be looked up — only estimated. The only question is whether the estimate is any good.

How much does the starting value actually control?

Recall the problem at the edge. The backward sum needs a number to begin from — something standing in for "everything that happens after this window stops". Where could that number come from?

Candidate 1  ·  0.00 — pretend the world ends here

The simplest choice: assume nothing follows the edge. It is obviously wrong when the episode is still running, but it is easy, and it is what this codebase actually did until July 2026.

Candidate 2  ·  13.18 — the truth

We are reading a recorded episode, so we can simply look. Take the rewards the agent actually went on to receive from step 129 to the end of the episode at step 501, discount them, and they sum to 13.18. That is genuinely what the future past this edge was worth.

The trainer cannot do this. At the moment it computes returns it holds only the 128 steps it just collected — step 129 has not happened yet. That is the entire reason a substitute is needed at all. We have the luxury of hindsight here precisely because we are auditing after the fact.

Candidate 3  ·  1.28 — what the code actually supplies

Unable to look forward, the trainer asks the critic to estimate it. The number the critic hands over, on this window, is 1.28. Why that is roughly a tenth of the truth rather than close to it is what section 4 is about — for now it is simply the number the code uses.

What that means

A hundredfold swing in what the agent is taught about step 128, with the environment, the actions and the rewards all held fixed. Almost the whole of that step's return came from the substituted number, not from anything the agent did.

Steps 121 to 124 make it sharper. Under the truth they are positive — those were good moments. Under the other two they are negative. Whether the agent learns "that was worth doing" or "avoid that" is decided by which number was put at the edge.

This is a solved problem — here is the field's answer

Nothing so far is unusual. Every reinforcement-learning implementation collects in fixed windows and faces exactly this edge, and the handling is settled well enough to have a canonical reference: Pardo et al. (2018), Time Limits in Reinforcement Learning. The rule is to distinguish two different ways a window can end.

Termination

start = 0

The episode genuinely ended — the agent died, or reached a goal. Nothing follows, so zero is not an approximation, it is correct.

Truncation

start = V(s′)

The window merely ran out while the episode continued. The future is real but unobserved, so the critic's estimate stands in for it.

Every mainstream library implements precisely this. Stable-Baselines3 passes last_values and dones into its return computation; OpenAI's Spinning Up has a finish_path(last_val) function that exists for no other purpose; CleanRL threads a next_value through its estimator loop.

And our code does this correctly

The July change added exactly this: zero on a real death, the critic's estimate on a truncation. The idea was right and the implementation of that idea is right. Windowing is not the defect, and neither is bootstrapping at the edge.

So why does the same technique misfire here? Because those libraries feed the critic a raw return, so the estimate it hands back is automatically in the same units as the rewards it joins. There is no opportunity for a mismatch. This codebase rescales the returns first — and that is the one thing none of them do.

Which part is actually at fault

Rescaling the returns causes two separate problems. It is worth seeing that only one of them involves the window edge at all:

Problem caused by rescaling the returnsNeeds a window edge?
The critic's target shifts every batch, for reasons that have nothing to do with the environmentno
The value handed back at the edge is in the wrong unitsyes

One of the two would exist with no windowing whatsoever. The other needs an edge — but only because the edge is where a rescaled number meets raw rewards; the rescaling is still what makes it wrong. Remove the windowing and two problems remain; remove the rescaling and all three disappear.

So read everything above as setting: the window, the edge and the starting value are the machinery inside which the defect operates, and they are worth understanding on their own terms — the last-third-of-every-window arithmetic is real and applies to any implementation. But the fault is not there. The rest of this document is about the rescaling: what it is (§3), what it does (§4–§5), and why no other implementation does it (§7).

2. Why anyone normalizes anything

Normalizing (or z-scoring) means rescaling a batch of numbers so they have an average of 0 and a spread of 1. It is a routine trick: it keeps the numbers a network sees in a comfortable range, which makes training more stable.

The question is which numbers you normalize. That single choice is the whole story here.

Raw units

−165 … +39

Actual reward values from this environment. Returns over a window have a spread of about 24.

Normalized units

−3 … +3

The same information, rescaled to average 0 and spread 1. Convenient, but no longer in the environment's units.

Hold on to these two colors. Amber is raw. Teal is normalized. The bug is what happens when they touch.

3. There are two recipes in the code, and only one is broken

The trainer has two ways of computing returns. A config setting picks one. They are meant to be interchangeable — but they normalize different things.

The three branches, side by side

All three live in the same function, within about twenty lines of each other. Only the last two lines of each differ — where the rescaling is applied, and to what.

MC — currentreturns = compute_mc_returns(...) # raw returns = (returns - mean) / (std + 1e-7) # ← rescaled HERE targets = returns # critic trained on RESCALED returns advantages = returns - values # ← never rescaled
MC_FIXED — newreturns = compute_mc_returns(...) # raw — identical call targets = returns # critic trained on RAW returns advantages = returns - values advantages = (advantages - mean) / (std + 1e-8) # ← rescaled HERE instead
GAE — existing, and already conventionaladvantages = compute_gae(...) # raw targets = advantages + values # critic trained on RAW returns advantages = (advantages - mean) / (std + 1e-8) # ← rescaled HERE

Read the last two blocks together

MC_FIXED and GAE have identical bookkeeping. Raw target, rescaled advantage, same epsilon. The only thing left separating them is the estimator itself — Monte-Carlo returns versus GAE's smoothed alternative, which Appendix A.5 shows are λ = 1 and λ = 0.95 of one family.

That is the entire point of the fix: it does not invent a third way of doing things, it makes the MC branch agree with the branch sitting thirteen lines below it.

The part that surprises people

MC is the broken one. GAE is fine. And every live config in this project uses MC — so essentially every run ever trained here carries the bug. The two GAE configs are the clean exceptions.

4. Where MC breaks

Training happens in windows of 128 steps. Steps near the end of a window have a problem: the window simply stops, so there is no "what happened next" to add up.

A fix was added in July to handle this — ask the critic what it thinks the future is worth, and use that as the starting value for the backward sum. (Not a random seed. Just the number the running total begins at.) The idea is right. The units are not.

01Critic predicts the value of the state past the window edgenormalized
02 · breakThat number becomes the starting value of a sum over actual rewardsraw
03Rewards are added backwards through the windowraw
04The result is normalized and becomes the critic's next targetnormalized

Step 4 is what makes the critic speak in normalized units in the first place — and step 1 reads its output straight back out. The loop closes, and the mismatch is baked in.

The same thing with actual numbers

correct starting value  =  13.18   // what the future past the edge is really worth
actual  starting value  =   1.28   // the same estimate, on the rescaled 0-to-1 scale

                      ratio ≈ 1 / 10

These are real numbers from a real training episode, not an illustration — the sourcing is in the next subsection. The starting value arrives roughly ten times too small in this window: denominated in the wrong currency, like settling a $13 bill with $1.28 because you read the price tag in a different unit.

First: what a "window" is, and what its edge means

The trainer does not process a whole episode at once. It grabs a fixed 128 steps of experience, learns from those, then grabs the next 128. That chunk is a window, and its edge is simply where the chunk stops.

The edge is an accident of bookkeeping. The agent's episode carries straight on across it — the episode used below runs 501 steps, so the edge at step 128 falls in the middle of an ordinary stretch of foraging. Nothing happens there. The agent cannot tell.

Second: why the sum runs backwards

A step's return is "everything that followed, discounted" [A.1]. You cannot know that until you know what followed — so the only way to compute it is to start at the end and walk back, reusing each answer to get the previous one:

return(step) = reward(step) + 0.95 × return(next step)

↓ the same recursion, in general form, in Appendix A.1

Each step inherits the one after it, discounted by 5%. That inheritance is what carries the starting value backwards through the whole window — and it is why one wrong number at the edge contaminates every step behind it.

At the very last step in the window there is no "next step" inside the chunk, so the recursion needs a number to begin from. That is the starting value. It stands for everything after the edge.

The part that actually bites

The leftover distortion is a function of where a step sits in the training window — and window position is not in the agent's observation. It sees satiation, pain, smells, what it can see, its own last action. Nothing about batching.

The reviewer strengthened this argument and also trimmed it. Stronger: the recurrent memory is reset only when an episode ends, never at a window edge, and episode phase drifts out of step with window phase — so window position is missing from the agent's whole history, not merely from its current observation. Trimmed: the average size of the artefact across positions is a function of things the critic can see, so part of it does get absorbed — as a mild bias toward short-sightedness, on the order of 15%. What is genuinely irreducible is the position-dependent residual around that average: noise rather than bias, worst near window edges.

And if the memory could fit the pattern, that would be worse, not better: the trunk is shared with the policy, so window-phase features would leak into action selection and into the value estimates that seed the next window.

Why the raw gap looks so much bigger than 0.16σ: the missing amount is (13.18 − 1.28) × 0.95k, where k is the number of steps back from the edge — about 11.9, shrinking only 5% per step. Against true returns that sit between 0.58 and 13.95, subtracting ~8 to ~11 does not dent them, it overwhelms them.

Correction, from an RL review of this page. The rescaling is done over the whole training batch — about 16,000 samples, spread ≈ 24 — not over this single window, whose own spread is 12.50. Dividing by the larger number makes the distortion smaller: in the units that actually reach the critic it is about 0.08 σ, half the 0.157 figure above. An earlier version of this note claimed the opposite. Note also this is one window: the error scales with how valuable the future past that particular edge is, so eventful windows are worse and quiet ones milder. That variation is unmeasured.

This was measured, not estimated, across four recorded training runs.

The honest headline

The July fix never worked. Before it, the backward sum started from zero; after it, the starting value arrives at about 4% strength — which is nearly the same thing. So these runs behave close to how they behaved before the fix existed, and the marginal harm attributable to the units mismatch, measured against the code that preceded it, is that same ~4%.

That is a smaller and more precise claim than "35% of targets are corrupted", and it is the one the evidence supports. The 35% figure describes how many targets the starting value should have reached, not how badly they were damaged relative to what came before.

The larger damage is dynamic, and it took an RL review to spot

Everything above is a snapshot of one batch. One further problem only shows up over training.

The critic chases a target that moves for no reason

Recentring and rescaling per batch means the number the critic is meant to output changes every iteration because of what else was in the batch. This is the exact pathology that motivated PopArt (van Hasselt et al., 2016) — learning against a target whose scale is itself drifting.

A second claim retracted here

This card used to carry a companion argument — that MC's policy step size quietly decays as the critic improves, and that the repair would remove that for free. It was measured and it is false; the retraction is at the end of §3.

6. Is it only about scale?

Almost — and the exception matters. The broken starting value is (future − average) ÷ spread where the correct one is just future. Two things are wrong: a division by the spread, and a subtraction of the average.

TermMeasured hereContribution to the error
÷ spread (σ)≈ 24dominant — shrinks the value ~25-fold
− average (μ)−3 to −4.7≈ 0.15 — negligible

So yes: in this environment the damage is essentially all scale.

Which means: would a small-scale environment be safe?

Largely, yes. If returns naturally had a spread near 1 and an average near 0, then the normalized value and the raw value would be nearly the same number — and this bug would be close to harmless. The defect only bites because this environment produces big returns.

But three things stop that from being a fix.

The spread is not one number

Measured per window it ranges widely: median 11, but 3.4 at the low end and 29 at the high end. So the error is uneven within a single run — some windows are barely touched, others badly distorted. And the badly distorted ones are the eventful windows, because that is what makes returns spread out.

Below a spread of 1, the error reverses

If the spread were less than 1, dividing by it would inflate the starting value instead of shrinking it. So the bug is not reliably "under-counting" — its direction depends on the data. It does not happen here, but it means the defect cannot be reasoned about as a fixed bias.

The moving target does not care about scale

Even at a spread of exactly 1, the critic would still be chasing a target rescaled by a different average and spread every window. That second defect is independent of how big the numbers are, and it is the condition that let the units mismatch exist in the first place.

And you could not fix it by shrinking the rewards

Rescaling the environment so returns came out near spread 1 would be tuning the world around a code defect — and it would not hold, because the spread grows as the agent improves. An agent that survives longer accumulates larger returns, so a scale chosen to make the bug harmless early would stop working exactly as the agent starts succeeding.

7. Why the repair is "stop normalizing the returns"

The obvious patch — convert the starting value into raw units before using it — fails for a concrete reason. The conversion factor comes from the spread of this window's returns, but you need the starting value before you can compute those returns. Circular.

And it would leave the deeper problem untouched:

The moving target

Because the rescaling is recomputed every window, the "right answer" the critic is chasing shifts every iteration — for reasons that have nothing to do with the environment. The agent's situation may be identical, but the number it is supposed to output changes because the batch it landed in happened to have a different spread.

The standard repair is the one GAE already uses: leave the returns raw, and normalize the advantages instead. You still get well-scaled numbers where the policy needs them, without a moving target and without two currencies meeting.

Worth noticing

The fix does not invent anything. It makes the MC branch work the way the GAE branch — sitting a few lines above it in the same file — already works. The current MC code is the deviation; the fix is the return to standard.

8. The honest cost of fixing it

Raw returns are big numbers, and that has a downstream consequence worth understanding before committing.

The critic learns by being pushed toward its target, and the size of that push is proportional to how far off it is — the raw arithmetic difference, not the percentage.

Target spreadPredictsTargetErrorPush size
today 10.51.20.70.7
after fix 2412291717

Both critics are equally accurate — each is off by about the same fraction. But one produces a push of 0.7 and the other 17. Same learning problem, bigger units. Like reporting a 2 °C error as 2000 millikelvin: identical situation, far bigger number.

Why that can hurt the policy

Gradient clipping is a safety cap: if one training update is too large overall, the whole update is scaled down to fit. The critical detail is that the cap is measured across the entire network at once — actor and critic share one budget.

// today
actor push 1  +  critic push 1  →  total 1.4  →  scaled to 36%

// after the fix
actor push 1  +  critic push 24  →  total 24  →  scaled to 2%

The actor's own push never changed, yet it shares a budget with something whose numbers exploded.

Correction — this arithmetic overstates the harm

The optimiser is Adam, which divides each update by a running estimate of its own recent magnitude. That makes it invariant to a constant rescaling of the gradients: if the clip binds by the same factor on every step, Adam largely cancels it after a short warm-up, and the policy's effective step size is nearly unchanged. The "2%" above is the raw-gradient story, not the applied-update story.

Two real harms survive that cancellation. Direction contamination: the encoder and memory are shared, so a value gradient 24× larger dominates the direction the shared trunk moves in, whatever the step size. Intermittent binding: Adam cancels a steady squeeze, not an occasional one — so windows containing a death, where the value error spikes, get a real one-off throttle that the surrounding steps do not.

Why this matters here specifically

The cap bites hardest on the largest updates — which in this environment means deaths and injuries, the events carrying the biggest rewards. So the plausible failure is that the policy gets throttled precisely at the moments that teach injury avoidance.

The run would end with an agent that never developed injury-dependent behaviour, and "modulation didn't help" would be indistinguishable from "the optimizer scaled the lesson down every time it appeared." Same numbers, opposite conclusions, no error message.

This is why the fix ships with a measurement and a pre-registered stopping rule rather than an assurance. We are not accepting the clipping problem — we are checking whether it actually occurs, having removed the one we know is real.

Correction — and the remedy I had wrong

I previously said that giving the actor and critic separate optimisers, each with its own cap, would dissolve this. That is wrong here. A single shared cap is the standard for PPO implementations with a shared trunk, and separating the optimisers would not help anyway, because the encoder and memory are shared — the trunk still receives the enlarged value gradient whichever optimiser applies it.

The standard first remedy is different and simpler: normalise the rewards upstream by a slowly-updated estimate of return spread, the way most PPO implementations do by default. That shrinks the spread from ~24 toward 1 and removes the pressure at source rather than measuring and gating it. If the stopping rule ever trips, that is the first thing to reach for — ahead of a stationary-scale value loss, or of switching to compressed value targets.

9. What this means for runs that already exist

The saving grace

Every run executed the same rule: in effect, no working edge bootstrap at all. That is a level playing field, and it is why comparisons between arms hold.

Correction: an earlier version said the bias was "uniform — same magnitude every run". That is not true. The error size depends on the value of the future past each edge, on each batch's spread, and on how good that run's critic was — all of which differ by arm. The cross-arm verdicts survive because every arm ran the same broken semantics, not because they were distorted by the same amount.

One correction falls out of this: the bug registry warns that runs trained before the July fix are not comparable to runs after it. Since the starting value arrives at about 4% strength, targets before and after are nearly identical — that warning is roughly 4% true.

10. What happened when the repair was actually run

Everything above is an argument from the code. This section is what the environment said. Three versions of the trainer were run side by side on the 10×10 jump-attack world (basic/04), five random seeds each, one million episodes per run, scored the only way this project scores anything — how many steps the agent stays alive.

ArmWhat it doesSurvival steps (5 seeds)
MC — the current coderescales the returns; the advantage is the left-alone difference138.2 ± 3.5
MC_FIXED — the repairidentical returns, raw critic target, separately rescaled advantages40.3 ± 0.8
GAE — the clean branchthe other estimator, same convention as the repair41.9 ± 0.7

The gap is not marginal and not noise: the arms do not overlap on a single seed. The repaired agent is 3.4× worse than the one this document calls broken.

The obvious objection, and why it fails

The budget was counted in episodes, and MC's episodes last longer — so MC actually consumed about 2.3× more environment steps. That is a real confound and it was checked: re-scored against steps rather than episodes, MC still leads at every matched budget. At 35 million steps for all three, MC is at 119.4 against 40.2 and 41.7. The advantage is not bought with extra experience.

The failure is more specific than "worse"

The repaired arms do not learn a mediocre foraging policy. They do not forage at all. In the GAE arm, the share of actions spent eating is exactly zero in 25 of 30 evaluation episodes. Measured as food eaten per step, MC eats once every 5.0 steps; the other two manage once every 23.6 and 19.4.

All three arms fall into the same trap early on — a local optimum where resting and slowly starving beats moving. Only MC climbs out of it: its starvation rate peaks at 58.5% and then falls to 26.9%, while the other two climb steadily to 54–55% and stay there.

Why: the policy never gets a turn

Three measurements, taken during training, tell one story.

Row one is the whole result. The trainer clips the gradient to a fixed maximum length of 0.5 before every update. MC's gradient is naturally below that and is never touched. The repaired arms produce gradients 150–300× too large, so every single update is squeezed back down to length 0.5 — and what survives that squeeze is whatever direction dominated, which is the critic's.

The reason it is the critic's is a shared trunk. In this architecture the actor and the critic are not separate networks: they read the same encoder and the same recurrent memory, and only split at the last layer. The two losses are added together, so one summed gradient shapes that shared trunk. When the critic is regressing on raw returns spanning roughly ±24 while the policy is working with advantages of spread 1, the critic's contribution is hundreds of times larger. The trunk is then trained almost entirely by value regression, and the actor is left reading out features that were never shaped to encode where the food is.

And the critic does not even succeed at that. Its target is a moving average over raw returns it never fits — explaining about 9% of the variance, with the value loss rising mid-training. The repair spends the entire budget on a regression that fails, and starves the policy to do it.

What was actually missing

Nine mainstream PPO implementations were surveyed for this project, and all nine use the raw critic target and rescaled advantages that MC_FIXED adopts. But all nine also carry something this codebase does not: a reward normaliser upstream of the return computation — running-statistics rescaling of the rewards themselves (VecNormalize), or a critic that learns its own output scale (PopArt). That component is what keeps their returns near spread 1 so the textbook convention is safe.

This project has no such component. MC's return-rescaling has been doing that job by accident — badly, with the units bug described in §4 as the price, but doing it. Removing it without putting a real normaliser in its place did not restore the convention; it removed the only thing holding the scales together.

The cleanest way to state the finding

MC and MC_FIXED consume byte-identical returns from identical code and differ by 98 survival steps. MC_FIXED and GAE use different estimators under the same rescaling convention and differ by 1.7. Scale predicts the outcome. The estimator does not.

Two things this section should not be read as claiming

MC is not a better policy across the board. Its typical episode is no better than the others' — median 40 steps against 38. The entire advantage lives in the upper tail: among episodes that survive at least 30 steps, MC averages 290.5 against 73.1 and 68.6. MC is not more reliable; it is the only arm that ever produces a long life at all.

And it is not an exploration story. The natural guess — that rescaling changes how much the agent explores — was tested and refuted, with the direction reversed: all three arms converge to a similar exploration level and MC ends up the least exploratory of the three.

Where this stands now

Longer 10-million-episode runs of all three arms are in flight. So far they argue against the gentlest reading — that the repaired arms are merely slower. Both are now well past five times the point where MC has clearly taken off (about 280k episodes) and neither has moved: 43.8 and 44.5 survival steps. That is early evidence for a stall, not a delay.

A fourth arm is running to settle the remaining ambiguity. Call it GAE_NORM: the GAE estimator, with MC's matched-scale rescaling. It fills the empty cell of a 2×2 — two estimators crossed with two scaling conventions — which is the only way to separate "matched scale is what helps" from "the Monte-Carlo estimator is what helps". Its predictions were written down before it was launched: near 139 means scale is the mechanism; near 42 means the estimator is.

11. What the missing piece actually is, and how it would be built

§10 ended on a claim that deserves to be concrete rather than gestured at: the nine mainstream implementations that use the raw-target convention safely all carry a component this codebase does not have — a reward normaliser upstream of everything else. This section says exactly what that component does and what adding it here would involve.

The idea in one line

Instead of rescaling the returns after computing them (what MC does) or rescaling the advantages after computing them (what the textbook convention does), you rescale the rewards themselves, as they come out of the environment, using a statistic that accumulates slowly over the whole run. Everything downstream — returns, critic targets, advantages — is then already on a sane scale, and no branch has to fix it up afterwards.

the canonical version (OpenAI Baselines VecNormalize)ret_acc = ret_acc * gamma + reward # a running DISCOUNTED return, per env ret_acc = ret_acc * (1 - done) # reset at an episode boundary update(ret_rms, ret_acc) # slow running mean/var over ALL steps seen reward = clip(reward / sqrt(ret_rms.var + 1e-8), -10, 10)

Three details in that snippet do the real work, and each is easy to get wrong.

It divides. It never subtracts the mean.

Note there is no - mean anywhere. That is deliberate in every implementation that does this, and Tianshou's source comments on it directly: subtracting the mean "will harm performances".

In this project the reason is much sharper than a general performance note. Our episodes have variable length — staying alive longer is the entire objective. Subtracting a constant c from every step's reward therefore adds a per-step bonus of −c for merely existing. In a fixed-horizon task that is a harmless baseline shift that cancels out. In a survival task it is a different objective: make c negative and the agent is paid to survive without foraging; make it positive and it is paid to die early. Scale the rewards freely; never shift them.

The statistic is over the discounted RETURN, not over the reward

ret_acc accumulates gamma-discounted rewards before the variance is taken. This matters because what needs to land near spread 1 is the quantity the critic predicts — the return — not the individual reward. Dividing by the standard deviation of single-step rewards would leave the returns off by roughly a factor of 1 / (1 − γ).

It is slow, and that is the whole point

The statistic is a running estimate over every step the run has ever seen, so it moves by a hair per iteration. Contrast MC's divisor, which is recomputed from scratch every batch — that is precisely the moving-target pathology in §7. A slow statistic gives the same scale benefit without it.

What it would take here

The obstacle is not the arithmetic, it is that this trainer is compiled. A running statistic is mutable state, and it cannot live in a Python object that a jitted function reads — it has to be carried explicitly, the same way the environment state and the recurrent hidden state already are. The current signature is:

train_iteration(model, optimizer, env_params, env_state, h_state, key, config)

and the change is to thread one more small piece of state alongside those two: four numbers per run — a per-environment return accumulator plus a running mean, variance and count.

PieceWhat it isWhere it lives
Return accumulatorone discounted-return running total per parallel environment, reset on episode endcarried state, shape (num_envs,)

The last two rows are where implementations of this usually go wrong, and neither produces an error message — a resumed run just quietly gets worse for a while, and a mis-scaled evaluation just reports the wrong number.

Why this is worth doing rather than picking a winner from §10

On this environment the returns have a measured spread of about 24, so the divisor would settle near 24 and the returns would arrive at roughly spread 1 on their own — the same place MC's rescaling puts them, but reached with a slow statistic instead of a per-batch one, and with no mean subtraction.

That combination is the one configuration this project has never run. It is also the only one that separates the two things §10 could not: whether matched scale is what helps, or whether MC's particular way of getting there carries a cost that only shows up late. If the reward normaliser lets the textbook convention match MC's early speed and keep the climb the raw-target arms are still showing at five million episodes, then neither existing branch was the right answer and this is.

A stronger variant exists: PopArt (van Hasselt et al., 2016) normalises the critic's target with a running statistic and then rescales the value head's output weights and bias so the un-normalised prediction is unchanged by the update — the drift is cancelled exactly rather than merely kept slow. It is the principled version; the reward normaliser above is the cheap one that nine libraries actually ship. Start with the cheap one.

Appendix A — the equations, and where they come from

Everything above was deliberately arithmetic rather than algebra — the worked episode in section 1 and the broken window in section 4 are the same objects in numbers. This appendix gives the general forms, shows how each follows from the one before, and then asks a question worth asking: how much of this is actually reinforcement learning's own invention?

A.1 — the return

The discounted sum of everything that follows, with the discount factor setting how much the future counts:

Gt=∞∑k = 0γk Rt+k+1

γ = 0.95 here, so a reward 14 steps away still counts for about half

Peel off the first term and what remains is the same quantity one step later. That gives the recursive form — the one the code actually computes, walking backwards:

Gt=Rt+1+γ Gt+1

This is the line from section 1. Nothing else in the document depends on the infinite sum; the recursion is the whole computational content.

A.2 — value, and the Bellman equation

The value of a state is the return expected from it under the current policy:

Vπ(s)=𝔼π[ Gt|St=s ]

Take the expectation of the recursion in A.1 and the same self-reference survives:

Vπ(s)=𝔼π[ Rt+1+γ Vπ(St+1)|St=s ]

That is the Bellman equation, and it is why a value estimate may legitimately stand in for "everything after the window edge" — the substitution section 4 is about.

A.3 — the advantage, and the TD error

Q is the value of committing to one action first; the advantage is how much better that action is than the state's average:

Aπ(s, a)=Qπ(s, a)−Vπ(s)

Neither is known, so both must be estimated. The cheapest estimator is the temporal-difference error — what one step of real experience says the value should have been, minus what the critic said:

δt=Rt+1+γ V(St+1)−V(St)

The fact everything rests on: if V is correct, δ is an unbiased estimate of the advantage. Every estimator below is assembled from it.

A.4 — MC and TD are two ends of one family

Look further than one step and the δ terms telescope. The n-step advantage estimator is:

Ât(n)=n − 1∑l = 0γl δt+l

Check the two ends. At n = 1 it is simply δt — one step of real reward, all the rest trusted to the critic. Let it run to the end of the episode and the intermediate value terms cancel, leaving:

Ât(∞)=Gt−V(St)

the Monte-Carlo advantage

So MC is not a different method from TD — it is the same estimator with n taken to the limit. The trade-off is the classical one: short n leans on the critic and is biased but steady; long n uses real rewards and is unbiased but noisy.

A.5 — GAE, derived

Rather than committing to one n, average over all of them with exponentially decaying weights:

ÂtGAE=(1−λ) ∞∑n = 1λn−1 Ât(n)

Substitute A.4, exchange the order of summation, and the geometric series collapses into something far simpler than it began:

ÂtGAE=∞∑l = 0(γλ)l δt+l

One discounted sum of TD errors, decaying at γλ. And its endpoints are exactly the two methods above:

λ=0⟹Ât=δt·λ=1⟹Ât=Gt−V(St)

one-step TD on the left, Monte Carlo on the right

Which reframes this project's two branches

The trainer's "MC" and "GAE" settings are not rival algorithms. They are λ = 1 and λ = 0.95 of the same estimator — and the config's own gae_lambda: 0.95 says so. Read that way the defect in section 4 is narrower than it first appears: a bug in how the λ = 1 branch handles a truncated window, in a family whose λ < 1 branch handles it correctly a few lines away.

Appendix B — is any of this reinforcement learning's own idea?

Mostly no, and the exceptions are informative.

IdeaOlder name, older fieldOrigin
Discounting the futurepresent value — economics and financeInterest arithmetic is ancient; formalised as discounted utility by Samuelson (1937). RL's γ is the economist's discount factor, γ = 1/(1+r) for interest rate r.
The returncost-to-go — dynamic programming and optimal controlBellman (1957). Control minimises accumulated cost where RL maximises accumulated reward; the sign flips and nothing else does.
The value function and its recursionBellman equation; the Hamilton–Jacobi–Bellman equation in continuous timeBellman (1957). In linear-quadratic control the value function is exactly xTPx, with P from the Riccati equation — the same object, solved in closed form.
Policy iteration over an MDPoperations researchHoward (1960), a decade before RL existed as a field.
Monte Carlo estimationMonte Carlo method — statistical physicsMetropolis & Ulam (1949). "MC return" is ordinary Monte-Carlo integration: estimate an expectation by averaging sampled trajectories.
Subtracting a baselinecontrol variates — Monte-Carlo statisticsA standard variance-reduction device. V(s) is a control variate for Gt: it correlates with the estimate and has known mean, so subtracting it lowers variance without adding bias.
Exponential λ-weightingexponential smoothing — time-series forecastingHolt and Winters, 1950s–60s. GAE's λ is the same geometric weighting of horizons.

What RL did contribute

Temporal-difference learning

Sutton (1988), with roots in Samuel's checkers player (1959) and in animal-learning theory. Dynamic programming needed a model of the world and swept all states; TD learns the same value function from sampled experience, bootstrapping from its own current estimate. That is genuinely new, and it is the step that made the Bellman machinery usable without a model.

The advantage function as an object

Baird (1993), "advantage updating". The idea of subtracting a baseline is older, but treating Q − V as the thing to estimate — and building algorithms around it — is RL's.

GAE itself

Schulman et al. (2016). Even here the ancestry is visible: it is TD(λ) — Sutton, 1988 — applied to advantage estimation rather than value estimation. The novelty is the application and the bias-variance analysis, not the geometric weighting.

So the honest summary: the return, the value function, discounting and Monte-Carlo estimation are all borrowed — from Bellman's dynamic programming, from economics, from statistical physics. What reinforcement learning added is learning these quantities from sampled experience without a model of the world: temporal-difference bootstrapping, the advantage as an estimation target, and the λ-family that interpolates between trusting your own estimate and trusting what actually happened.

Which is worth holding onto while reading section 4. The bug there is not in any deep idea. It is in the bookkeeping of one truncated sum — the most mechanical part of the whole stack.
