## Verdict

The plan is to delete the project's original episode-video renderer, stop the current renderer borrowing one function from it, and rename the current renderer's script so it no longer carries "v2". The plan's central discovery is right and I re-verified every part of it: the pixel audit — the instrument that checks a rendered dashboard frame for text printed over text, dropped panels and similar defects — proves it can detect anything only by pointing at defects that live in the two old renderers, so deleting them before replacing those proofs would leave the audit unable to express its own controls. The plan's ordering (census → move the shared function → replace the audit's proofs → delete → rename) is correct, and the user's decision to wait for the fourteen live training runs makes the live-cluster exposure moot for the one step that has it.

**What is wrong is narrower than the ordering: Step 2's stated scope is too small for its own exit gate to pass.** The gate (CP2.7) asks the audit's control suite to pass with both old renderers moved out of the way. As scoped, it cannot: the audit's frame loader imports a helper from the old renderer on every call — including on the "hand the audit a frame" path that Step 2 builds on — and the audit's control table and its `--controls` command still reach for the old renderers unless Step 2 changes them, which the plan lists as optional. A developer who follows the plan as written reaches CP2.7 with a red suite and no scheduled fix, which is exactly the state the plan warns tempts someone to delete the controls. Three further Moderate findings: the instruction for moving the old files aside (`git stash`) cannot do what it says and, in this repo of parallel sessions, would sweep another session's uncommitted work into the stash; Step 2 says it is safe under live runs, but that is only true if the "deliberate breaks" are applied inside the test process rather than as a hook in the renderer package, which the plan leaves open; and the byte-identity gate on the moved function assumes video encoding is reproducible run-to-run, when the project's own record shows two renders of the same recording by the same renderer differing in size.

**Nothing in this plan can destroy data.** Every deletion is `git rm` of tracked files; nothing under `results/` is moved, and the only hazard to anyone's work is the mis-specified `git stash`.

**What would make it SOUND:** widen Step 2's scope to name the loader import, the control table and the `--controls` command as mandatory changes; replace `git stash` with a `mv`-out / `git checkout --` back that touches only the two files; state that mutations are test-process monkeypatches only (or give Step 2 the same wait gate as Step 1); and make CP1.4 establish encoder determinism first or fall back to decoded-frame equality. None of these is more than an hour of planning work.
