# Plan review: behaviour-test sweep — on-node scoring, episode archives, migration of old folders

Reviewed by: plan-reviewer · 2026-10-07 · plan at commit `fa7fa715`
Plan: [[SWEEP_EPISODE_BUNDLES_AND_ON_NODE_MEASURES]] (`docs/develop/active/refactors/SWEEP_EPISODE_BUNDLES_AND_ON_NODE_MEASURES.md`)

## Verdict

**NOT READY — but both blocking problems are about *ordering*, not design, and each is fixed by one added precondition.**

The plan rewrites how the behaviour-test sweep (the pipeline that replays every saved checkpoint of a trained agent in fixed test scenes and scores 11 behaviour measures) stores and scores its episodes. The design itself is careful: archives keep every original file byte for byte, originals are deleted only after a re-check, and the score-equality gates compare against results the old system actually produced. Two things would still go wrong if it were implemented as written:

1. **The "hold" that protects another session's exactness checks does not cover new sweeps.** The plan stops the migration from deleting old episode folders that the neuromodulation session's tools read. But the moment the new code goes live, every *new* test launched into those same folders is written only as an archive — and three of those tools, on finding no folder, quietly fall back to a weaker check or skip it. That is precisely the silent weakening the plan says it must prevent.
2. **Editing the worker script while three sweeps are running can hang them.** Bash reads a running script from disk a piece at a time; the three no-healing sweeps launched at 16:03 today are still running the current worker, and its last two lines (which write the "done" marker) are read *after* the episodes finish. Editing the file in place in the meantime most likely leaves the sweeps without a done marker and their drivers waiting forever — the very silent hang this plan sets out to fix. The plan has no step that accounts for the running sweeps.

Everything else is Moderate: mostly ways the new liveness checks can still miss a death, and ways the verification can pass while checking less than it appears to.

**Severity legend:** 🔴 Critical = fix before going further · 🟡 Moderate = likely costs a re-run · 🟢 Low = cosmetic · ❓ Open = an assumption nobody has verified yet.

## Recommendations on the open decisions

- **D1 — where scoring runs: on the node, after the test program, from the node-local copy (plan's choice). Agree.** It keeps the test program and the Dreamer source untouched and scores the same bytes. Conditions: pack before scoring (M3), node-env pre-flight (M8), finisher errors logged rather than discarded (M5). Scoring inside `eval_rollout.py` would add a second scoring path for Dreamer and is rejected for good reason.
- **D2 — folder name: keep `_scratch/`. Agree**, provided the README stops calling it "transient; safe to delete" in the same commit (planned).
- **D3 — scope: avoidance roots only, others inventoried. Agree.**
- **D4 — pilot backup: a full copy is not the best use of the same I/O.** Instead: (1) the independent cross-host check of M1(b) on the pilot before its first deletion; (2) a one-time copy of the small irreplaceable files — every per-scene CSV, figure and `_provenance/` under `results/eval/avoidance/` (MBs, not GBs) — before the first `delete`, because the path guard is the one thing whose bug would hit the files the pages read; (3) in M0, flag every root whose source checkpoints no longer exist: those episodes cannot be regenerated, and they should get either a backup or the same independent check before deletion. If the user wants belt-and-braces on top, a `tar` of the pilot root alone (~1.6 GB) is affordable once.
- **D5 — coordination: the neuromodulation session ports R9–R12** (it has uncommitted edits in `obs_manipulation/run.py`; a second editor would collide). Order: `episode_bundle.py` lands alone → that session ports → new worker goes live (C1). Lift the hold per root only after a positive check: run the ported `_parity` on an archive-only cell and confirm it reports `exact`, not just that it imports.

## What would flip the verdict

- C1: the plan's phase order puts the F9 ports (or a legacy-folder dual write for held roots) **before** the new worker goes live.
- C2: Phase A carries an explicit precondition that no live sweep uses `sweep_worker.sh` when it is edited (and, ideally, launches a per-launch copy of the worker).

With those two lines added, the verdict becomes SOUND WITH CONCERNS (the Moderate items above).

## Cost of being wrong

C1 costs no data but quietly lowers the evidence bar of another session's case study: steps tested after the switch would pass on the weaker check and be reported as if they had passed the exact one — a wrong-confidence claim that nothing would flag. C2 costs the three running sweeps (~20 minutes each plus the reruns) and reproduces an hours-long silent hang. The deletion path itself is well guarded; its worst remaining case (M1, M7) is losing regenerable episodes (hours of re-testing) or a silently wrong CSV row — and is unrecoverable only for roots whose checkpoints are gone.
