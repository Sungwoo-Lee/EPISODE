# Plan review: analysis tooling for "What Both Agents Compute"

**Reviewed**: [[ALGORITHMIC_NULL_ANALYSIS_TOOLING]] (`docs/develop/active/neuromodulation/`), read at HEAD 2026-09-29, before any code exists.
**Reviewed by**: plan-reviewer

## Verdict

**NOT READY.** The plan is careful about the things that usually go wrong here (restore checks, row alignment, episode-grouped splits, no `nnx.sow`), and most of its line-number claims check out against the code. Two things must change before implementation, because each would turn into a wrong sentence on the page rather than a failed run:

1. **The headline "wake-up" definition has silent degenerate cases.** The chosen rule — the checkpoint where a measure has covered half of its rise from the first checkpoint to its final value — gives *checkpoint 0* for any measure that **falls** over training, and a noise-driven answer for any measure that ends roughly where it started (rises then returns). Neither case raises an error. The freeze cost, the per-term gradient shares and ρ on some arms can all do one of these. The fix is small: define the crossing in the *direction* of the change, refuse to report a wake-up when the total change is inside the checkpoint-to-checkpoint noise, and anchor the start at the untrained network where that is computable.
2. **No decision rule exists for "the two agents compute the same thing" before the first similarity numbers are seen.** The plan schedules an interim seed-yardstick figure (Stage 4b) and pilot similarity figures (Stage 3) but names no threshold for "modulated-vs-ordinary similarity is inside the ordinary-vs-ordinary range". Whatever threshold is written after those figures exist is post hoc. The rule must be written into the manifest before Stage 3 runs.

Everything else is Moderate or lower and is listed in the table.

## Assumptions the plan rests on

- ❓ `jax.make_jaxpr` text can be captured for the `nnx.jit`-decorated `get_action_and_value_nnx` and for `ppo_loss_fn` with an NNX model argument, and is textually deterministic across two processes. Feasible (split graphdef/state, or `.lower().as_text()` on the jitted function) but not demonstrated; Checkpoint 1.3 is the speed gate, so the mechanism must be settled first.
- ❓ Compute for Stage 4 is unstated: 16 level-05 runs × 50 checkpoints of `replay.rollout` for ρ, plus freeze sweeps at 10 checkpoints × 2 heads × paired rollouts, plus six May runs. No episode count per checkpoint, no node or GPU class, no wall-clock estimate. It runs "in parallel with Stage 3" on unnamed hardware.
- ❓ The join from a WandB `loss/grad_norm` record to an episode count (§7) — the plan correctly flags this as unverified; it decides whether the total-loss share can be binned to checkpoints at all.
- ❓ Level-05 checkpoints start at 200 k episodes; any wake-up earlier than that is invisible to every checkpoint-resolution measure (see finding 1c).
- ❓ `launch_collection.py`'s "finished" detection on the two untagged 15:36 logs (finding 6).
- Verified in this review: stored actions are greedy argmax (`policy_mode: deterministic_argmax`), so 100 % self-agreement is attainable; logits and values are **not** stored, so no stronger stored-output check exists; `nnx.GRUCell` returns `(h, h)` so `rnn.raw == rnn.state` for the ordinary agent; both studies save `activation: relu`, `use_layer_norm: true`, `perceptual_noise.enabled: false`, `max_steps: 500`; the gate-bias init confound (registry line 107) does not apply because `rnn_mechanism: activation` builds `nnx.GRUCell` for both arms; the construction order encoder → LayerNorm → GRU → actor → critic → modulator holds at `recurrent_ppo_network.py:400-460`; the checkpoint payload carries `stage`; no store of a continual run exists today; `pilot_readout.py` never touches stores or the collector.

## Known-bugs pass

Done by reading the registry directly. The plan's "L107 … L461" are **line numbers** in `KNOWN_BUGS.md`, not row IDs; each cited line matches the described row. No registry row covers teacher-forced replay, activation capture, or the wake-up measure. Nothing found here that the registry should record yet; `bug-curator` is not needed until finding 6 (glob under-coverage) or 7 (shared figures directory) actually bites.

## Cost of being wrong

No data-loss hazard and no training relaunch is at stake; the tooling runs on saved checkpoints and stores. If finding 1 or 2 is left as is, the cost is a wrong sentence on a page that is meant to be read as evidence — "the modulator was awake from the start" from a falling measure, or "same computation" from a threshold chosen after the numbers — and the May replication's 12 stores (~6 GB, a few GPU-hours) would need recollecting only if finding 8's fingerprint choice is made carelessly.

## What flips the verdict

Finding 1 fixed in `wakeup.py`'s spec and tests (signed crossing, minimum-change guard, untrained anchor), and finding 2's `decision_rules` block written into the May manifest schema and committed before Stage 3 runs. Moderate findings can be accepted knowingly, but 3 and 4 are the ones that decide whether the similarity numbers are about the right tensors.

# Re-review (Revision 1 + pre-registered decision rules), 2026-09-30

**Reviewed together**: the revised plan (`f93b3634`) and `experiment-designer`'s rules file `docs/experiments/active/modulator_clues/algorithmic_null_decision_rules.yaml` (`b7fe1431`) with its three manifests (`algorithmic_null_pilot.yaml`, `algorithmic_null_mayrep_interim.yaml`, `algorithmic_null_mayrep.yaml`). ## Verdict

**NOT READY** — but for a different and cheaper reason than last time. The two Critical findings of the first pass are substantively closed: the wake-up rule is now signed, guarded and anchored at the untrained network, and a real decision-rules file exists before any number does. What is not closed is that **the plan and the rules do not describe the same tooling**. The plan tells the developer to read a machine-readable `reads`/`outcomes` block from a `decision_rules_ref` key, and to stop and ask if the block has another shape; the designer wrote prose rules in a separate file pinned by a whole-file sha256 under a `decision_rules` key in every manifest, the pilot included. Followed literally, the plan halts on day one — or the developer improvises an evaluator whose reading of the prose nobody registered. Around that, the rules read five quantities the plan never computes, the rules' own recipe for the untrained reference networks is the wrong one (it is mine, from the first review), and the wake-up thresholds are still not written anywhere the tooling reads. Each fix is a few lines; none needs a rerun of anything. Where the plan and I disagreed, the plan is right on all four points (untrained key, rules location, `stage_end` semantics, fingerprint strictness) — details in §Disagreements.
