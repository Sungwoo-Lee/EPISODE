Loops and Graphs

Two new names for one old instinct: stop typing every step yourself, and build the structure that does it for you.

PURPOSE

The people who build software on large language models keep naming new kinds of “engineering”. Two of the newest are loop engineering and graph engineering. Loop engineering means designing the repeat-until-done cycle that drives one AI agent, instead of prompting it by hand one step at a time. Graph engineering means designing how several such agents, their tasks and their shared record of progress fit together. This page explains both with diagrams. It is written for a reader who has used a chat assistant but has not followed the new vocabulary.

The page lives in this repository for a practical reason. The project already runs a team of Claude agents that plan, review, build and verify, plus skills that repeat a task until a condition is met (§5). Having names for these patterns makes it easier to see where our own setup is strong and where it is fragile.

The claim is modest. Both terms name ways of working, not new algorithms, and neither changes the model underneath. Both are only a few months old, and sources do not yet agree on exact definitions. §6 says where they disagree.

01 Five layers, one inside the next

The clearest map of the vocabulary comes from a survey posted in August 2026 by Feng and 34 co-authors {{CITE:feng}}. It lists five kinds of engineering in the order the field turned to them. Each one works on a wider unit than the one before.

prompt
Wording one request well: instructions, examples, constraints.
context
Choosing what information the model can see when it answers: retrieved documents, earlier results, compressed history.
harness
Connecting the model to things outside it: tools it can call, memory it can write, skills it can load.
loop
Running the model and its harness repeatedly, with feedback, until the goal is backed by evidence.
graph
Organising many loops, meaning many agents, and the tasks and state between them as an explicit structure.

02 Loop engineering

The shortest definition is Addy Osmani's, from June 2026 {{CITE:osmani}}:

“Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead.”

In ordinary use of a chat assistant, you are the loop. You ask, read the answer, decide what to ask next, and decide when you are finished. Loop engineering moves those decisions into a written specification and a program that repeats. The agent works, a check judges the work, and the loop goes round again until the check passes or a budget runs out.

What goes into a loop

Macedo's preprint studies fifty loops people have actually built. It argues that each one comes down to a loop specification with five parts {{CITE:macedo}}. IBM's explainer describes the same running cycle as goal, action, observation and adjustment {{CITE:ibm}}. That is the thought-action-observation pattern introduced by the ReAct paper in 2022 {{CITE:react}}, called reason-act-observe below.

The smallest real loop

The best-known example predates the name. In July 2025 Geoffrey Huntley described running a coding agent inside a shell loop that never ends. He called it the Ralph Wiggum technique {{CITE:huntley}}:

← the code is wider than the box — scroll it sideways

while :; do cat PROMPT.md | claude-code ; done

Every pass starts a fresh agent with an empty context. The same prompt file is the goal. A prioritised to-do file and a folder of specifications on disk are the memory, and each pass does exactly one task. Huntley's check is the project's own tests and build. He calls it “backpressure”: a pass that breaks the build is pushed back by the next pass, which sees the failure {{CITE:huntley}}. Measured against Figure 3, the trigger is “the last pass ended”, and the stop rule is a person pressing Ctrl-C. Macedo's fifty-loop survey found the same weak spots in general. Most loops verify their own work (70%) and define an explicit end state (74%), but automatic triggers and memory that persists across runs are still underdeveloped {{CITE:macedo}}.

Not the reinforcement-learning loop

This project trains reinforcement-learning agents, and their agent–environment loop (act, observe, receive a reward, act again) resembles Figure 3, though the reward is a per-step number, not a verifier's pass-or-fail verdict against a goal. The bigger difference is what changes. In reinforcement-learning training, the experience the loop generates is used to update the agent's weights, so the agent itself learns. In loop engineering, the model's weights never change. What improves from pass to pass is the work product (code, a document) and the files in memory. A loop-engineered agent is not learning in the reinforcement-learning sense, and “the loop got better” means the artifact did.

How loops go wrong

  • Unattended mistakes. A loop running overnight makes its mistakes overnight. Huntley reports placeholder code written only to satisfy a compiler, and mornings that start with a broken build {{CITE:huntley}}.
  • Comprehension debt. Code ships faster than anyone reads it, so the team understands less and less of what it owns {{CITE:osmani}} {{CITE:ibm}}.
  • Cognitive surrender. Using the loop to avoid thinking rather than to think better. Osmani's advice is to build the loop “like someone who intends to stay the engineer, not just the person who presses go” {{CITE:osmani}}.

03 Graph engineering

A single loop, however well built, runs out of room. The survey by Feng and colleagues names what it cannot supply on its own: “heterogeneous expertise, interdependent subtasks, parallel execution, independent verification, and persistent state” {{CITE:feng}}. A single agent cannot review its own work independently, and it cannot be in two places at once.

Graph engineering responds by writing the relationships down. In the survey's words, it “uses graph structures as the core substrate for externalizing relationships among tasks, components, and runtime states” {{CITE:feng}}. A graph here is the ordinary mathematical object: nodes joined by arrows. The survey keeps three of them, one for each kind of relationship.

The survey's examples show what each graph buys. LLMCompiler compiles a plan into a dataflow graph so that independent tool calls run in parallel. AutoAgents creates specialist roles and a plan for how they collaborate. AFlow has a model search over workflow code for a better arrangement of steps {{CITE:feng}}. Whatever the system, the first design choice is the graph's shape.

What the survey says is still open

Can the graph build and improve itself?
Most graphs today are written by hand. The survey names self-evolving graphs, ones an agent system discovers and revises across many runs, as an open problem {{CITE:feng}}.
What would a runtime built for graphs look like?
Current frameworks were adapted from one-agent, one-step-after-another designs. The survey calls for runtimes, and even operating-system-style layers, that treat scheduling, resources and failure recovery as properties of the graph {{CITE:feng}}.
How do you measure a system rather than an agent?
Benchmarks score whether the task got done. Few test graph-level properties, such as whether the coordination was correct or how the structure adapted over time {{CITE:feng}}.

04 Side by side

The two ideas are not rivals. A graph is made of loops, and every agent in Figure 4 runs one. They differ in what the engineer designs and in what goes wrong when that design is weak.

05 This repository already does both

None of this is foreign to grid_world_pain. The agent team in CLAUDE.md and the flows in docs/AGENT_PLAYBOOK.md form a graph designed by hand, and several of its nodes run loops of their own. Figure 6 draws the flow for adding a feature, exactly as the playbook writes it.

Seen through §2, the repository's loops are easy to spot:

/wake
A loop specification in miniature. The trigger is a timer, the goal and stop rule are a done-condition the user states, and the skill re-arms itself until that condition is met.
/loop
Runs a prompt or command on a repeating interval. It supplies the trigger; the check and the stop rule are whatever the repeated command does.
format gate
Every artifact, this page included, goes through publish-page. artifact-format-reviewer renders the page in a real browser. A “do not publish” verdict sends it back to be fixed and re-checked.
memory
The daily diary, the LLM Wiki and Claude's built-in memory play the part of memory on disk. They are how a fresh session finds out what earlier sessions did.

This page's reading, not a finding

By the survey's standard, the team's graph is static: the playbook fixes the flows, and agent-manager chooses among them per job rather than building a new graph. Its runtime state is also thin. The diary records that a step happened, but no checkpoint lets a half-finished multi-agent job resume where it failed. If either becomes a bottleneck, §3 is where to look.

In short

  • Loop engineering designs one agent's cycle (trigger, goal, check, stop rule, memory) so the agent reaches a verified finish without a person typing each step.
  • Graph engineering writes down the structure among many agents: which tasks depend on which, who hands work to whom, and where the job stands. With that written down, work can be split, run in parallel, checked independently and recovered.
  • One contains the other. Every node in the graph is itself a loop.
  • Neither changes the model, and neither removes review. Both move human judgment from writing prompts to designing checks and structure.

06 How settled are these terms?

Not very. Treat everything above as a snapshot from September 2026.

Who coined them, and when?
The practice came before the name: Huntley's loop dates from July 2025 {{CITE:huntley}}. The sources this page read that use “loop engineering” are all from June–July 2026 {{CITE:osmani}} {{CITE:macedo}} {{CITE:ibm}}, and none of them claims to have coined it. “Graph engineering” as a named paradigm comes from one August 2026 preprint {{CITE:feng}}, which has not been peer reviewed.
Do the sources agree on what a loop is made of?
Partly. Osmani lists tooling: scheduled automations, isolated worktrees, skills, connectors, sub-agents and persistent state {{CITE:osmani}}. Macedo lists parts of a specification: trigger, goal, verification, stop rule and memory {{CITE:macedo}}. IBM mixes the two {{CITE:ibm}}. This page follows Macedo, because those parts describe any loop rather than one toolchain.
Is graph engineering just workflow graphs under a new name?
It overlaps with them. The survey's scope is wider than a workflow of steps: it also covers the agent graph and the runtime state graph (Figure 4) {{CITE:feng}}. Other names for nearby ideas circulate, such as “flow engineering”. This page found no primary source for them and does not compare them.
