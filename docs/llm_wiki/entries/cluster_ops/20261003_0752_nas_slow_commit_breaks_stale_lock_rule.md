# The 10-minute stale-lock rule misfires when NAS commits take 25+ minutes

## Key conclusion
CLAUDE.md allows deleting `.git/index.lock` when it is 0 bytes and more than 10 minutes old, on the premise that no live git operation holds a lock that long. On the night of 2026-10-03 shared-folder commits ran for over 25 minutes each (process blocked in `wait_for_response`, i.e. waiting on the NAS), so a 13-minute-old empty lock belonged to a live commit, and a sub-agent following the rule tried to remove it. The removal appears not to have taken effect, but the rule's premise does not hold under heavy NAS load.

## Evidence, measurements, facts
- 03:14: sub-agent attempted `rm` of a 0-byte, 13-min-old lock held by the parent's live `git commit` (pid visible, fd 3 -> .git/index.lock).
- Six consecutive commit attempts each hit a 25-min `timeout`; one pathspec commit spent >17 min in `wait_for_response` with no child process (no hook involved).
- Load at the time: ~15 MB/s aggregate NAS read by analysis sweeps + a 700 GB store validation + another app's NAS scanner; load average ~49 on 20 cores.
- A sparse git worktree on the same NAS committed in minutes — the full-tree index refresh (~5,400 lstat calls) is what is slow.

## Decisions and actions
- Logged in the diary; `git fsck` deferred until the NAS is quieter.
- Proposed to the user (not yet decided): raise the threshold, or additionally require that no process has the lock file open (`/proc/*/fd` scan), before deleting.

## Open questions and follow-ups
- Run `git fsck` on the shared repo.
- User decision on changing the CLAUDE.md stale-lock rule.
