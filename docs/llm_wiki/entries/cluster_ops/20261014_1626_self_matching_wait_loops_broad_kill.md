# Wait loops that search for their own command never end; broad kills hit other sessions

## Key conclusion
`pgrep -f <pattern>` matches against full command lines, and the loop's own `zsh -c "until ! pgrep -f '<pattern>' ..."` contains that pattern. So the loop always finds "a match", which is itself, and never ends. Killing such loops by a broad pattern is worse: in a repo shared by several Claude sessions, the pattern also matches other sessions' processes.

## Evidence, measurements, facts
- 2026-10-11: three of the Admin session's background tasks hung on `until ! pgrep -f "git commit -q -F $S"` after the commit had already landed.
- Cleanup with `pgrep -f 'until ! pgrep'` plus kill also ended two older wait loops belonging to the Behavior session (pids 823199 and 855163). Behavior later confirmed that nothing it needed was lost; the loops were stale.
- The same kind of self-match was recorded before for a remote `pkill -f` killing its own `bash -c` wrapper: [[20260819_1944_run_command_parallel_race_and_remote_pkill_self_kill]].
- A related zsh gotcha from the same session: an unquoted `=name` (as in `tmux -t =gpu-monitor`) is expanded by zsh as a command-path lookup. Quote it: `-t '=gpu-monitor'` or `-t gpu-monitor`.

## Decisions and actions
- To wait for a command, run it as a background task and wait for the harness's completion notification. Don't poll with pgrep.
- If polling is unavoidable, use a pattern that cannot match itself (`pgrep -f '[g]it commit'`) or match on an exact PID (`while kill -0 $PID`).
- Kill only PIDs this session started (task IDs or recorded PIDs). Never kill by a pattern that other sessions' processes could share.
- When a broad kill does hit another session, tell that session and the user right away.
