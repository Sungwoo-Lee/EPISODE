# Full trajectory-store validation is infeasible from the container; sweeps scale with more readers

## Key conclusion
The collection driver's `--validate-only` pass re-reads every parquet byte of every store, and `validate_store_shapes` does too; for the thirst task (18 stores of 34–45 GB) that was days of reading at the night's 5–10 MB/s per process, and it competed with the analysis sweep that needed the same NAS. Each reader was latency-bound (state D, low CPU), not bandwidth-bound, so adding parallel readers to the analysis sweep raised throughput roughly threefold.

## Evidence, measurements, facts
- Store sizes: 34 GB (20x20 world) to 45 GB (10x10 world) per 1 M-episode store.
- Validation process read 16 GB in ~1 h while on its first store.
- Basic-behaviour sweep: ~4.1 shards/min with 3 workers -> ~13 shards/min with 8 workers (developer's shard-position measure; `rchar` does not count pyarrow reads).
- The sweep reads only needed parquet columns; `obs_true` dominates volume.

## Decisions and actions
- Stopped both full validations; rely on the analysis sweep's own per-step integrity checks (hydration rise <-> on pond cell, death-code range, config draws) as the de-facto store check.
- Run analysis sweeps with ~8 workers when the stores are this large.

## Open questions and follow-ups
- Full byte-level validation of the thirst stores is still not done; schedule it on lab nodes or at an idle time if needed.
