# Git branch files stuck 'delete pending' on the NAS

## Key conclusion
On the SMB NAS, a file that git replaces can stay "delete pending": it is listed in the folder, but opening it fails and its name can't be reused. For a branch file, git then treats the branch as missing, and the next commit is a bogus first commit holding only the committed files. The fix was to delete the stuck names on the NAS side through Synology File Station. After that, the files were rewritten from known-good values. A remount alone was not enough.

## Evidence, measurements, facts
- 2026-10-07, 17:43 KST: Training's commit c035969b was good, on top of GitHub's fdb2f7d7. While git was updating the branch file, `refs/heads/v5.0` went delete-pending. Two retries then produced bogus single-file root commits (ff4bcc21, 2f3e515a). `packed-refs` went the same way at about 17:50, during a repair attempt.
- `git update-ref` and write-then-rename both failed ("Permission denied").
- A full unmount and remount of the container's NAS mount on 10-08 did not clear it. Lab nodes 104 and 109 also listed both files and couldn't open them, so the hold was on the NAS side or with some other client, not in this container.
- An earlier case on 10-02: a doc file got stuck the same way after `git checkout`, and cleared by itself after a few days. Writing it under a temporary name and then renaming it worked there.
- Repair on 10-08, after the user deleted both files in File Station:
  - wrote `refs/heads/v5.0` = c035969b5260f2f48b3d4a2224542af6396421a9;
  - restored `packed-refs` byte for byte from Training's backup (`tmp/20261007_175000_git_incident_packed-refs.bak`);
  - `git fsck` was clean, and `git status` showed 139 real changes instead of 6,351 "new" files;
  - pushed fdb2f7d7..c035969b as a fast-forward.

## Decisions and actions
- Signs of this failure: a branch "disappears", or `git status` suddenly shows thousands of new files. Stop all commits at once (board note plus messages to sessions). A commit made in that state is a single-file root commit, and force-pushing it would wipe GitHub's copy (compare the 10-03 plumbing-commit incident).
- Nothing in the stuck files is irreplaceable: a branch file holds one commit ID, and packed-refs can be rebuilt from a backup or from GitHub. Record the good commit ID and back up packed-refs before repairing.
- NAS-side remedies, mildest first: delete the stuck files in File Station; end other SMB connections (Resource Monitor); restart the SMB service; reboot the NAS.

## Open questions and follow-ups
- The process holding the files was never identified. Candidates: VS Code's git integration on another machine (ruled out once by closing it), Synology indexing, antivirus or backup tasks, or another SMB client.
- Confidence is medium: this was reconstructed from the session record, and the root cause is unknown.
