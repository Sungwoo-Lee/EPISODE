# Run registry went stale: its rebuild is an instruction, not code

## Key conclusion
`scripts/lab/run_registry.py build` was meant to run "after every launch and resume by whoever launched"
(training-runner §4e, registry README). Nothing in the launch path calls it, so any launch outside the runner, and
any status change (finish, stop), leaves `docs/experiments/run_registry/runs.csv` stale until someone rebuilds.

## Evidence, measurements, facts
- Last rebuild 2026-10-13 23:51 (14 seed runs launched by the runner); 13 later watcher launches absent until a
  manual rebuild on 2026-10-14 15:47, which then listed all 27 started seed runs correctly.
- Full rebuild: ~5 s (plain and `--live`), on 1,178 sessions / 1,161 WandB runs.
- Plain build marks "running" only if WandB wrote in the last 30 min: 18 running vs 20 with `--live`.
- `run_registry.py resume <id>` returned the correct newest checkpoint folder, WandB id and full command, and
  warned that the run still looked alive.

## Decisions and actions
- Rebuilt and committed (`edcb5099`). Documented the limits in TRAINING_OPERATIONS §4 and §8.

## Open questions and follow-ups
- Automatic rebuild still undecided by the user: options proposed were (a) `find`/`resume` rebuild live before
  answering plus a delayed rebuild in `run_command.py` after any train.py launch (recommended), (b) launch hook
  only, (c) periodic 30-min rebuild; and whether to keep committing runs.csv.
