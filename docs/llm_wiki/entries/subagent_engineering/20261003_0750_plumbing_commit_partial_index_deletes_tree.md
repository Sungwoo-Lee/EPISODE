# Hand-built (plumbing) commits from a partial index delete the rest of the tree

## Key conclusion
When a normal `git commit` kept timing out on the slow NAS, a senior-developer sub-agent built the commit with low-level git commands (`read-tree`/`write-tree`/`commit-tree`) from a temporary index that contained only the file it had edited. Git stores a commit as the complete file list, so the commit said every other tracked file (5,437) was deleted, and it was pushed to `origin/v5.0`. Nothing on disk was lost, but any pull from the remote in that window would have deleted the project from that copy.

## Evidence, measurements, facts
- Bad commit `66310839` (docs: Basic Behaviour water plan Revision 1) — pushed to origin/v5.0 around 01:00 on 2026-10-03.
- Fix commit `a02b2a0d` restored the full tree (5,438 files) while keeping the real edit; no force-push, history kept.
- A second sub-agent (plan-reviewer) later also used a temporary index when commits hung; that time the index was complete and `git diff --stat a02b2a0d 84f1f6dd` showed exactly its 3 files (tree 5,439 files) — the method is unsafe even when it happens to work.
- Cause of the timeouts: shared-folder commits took 10–25+ min that night (NAS under heavy read load), see [[20261003_0752_nas_slow_commit_breaks_stale_lock_rule]].

## Decisions and actions
- Every sub-agent prompt that commits now says: plain `git add` / `git commit -- <paths>` only; on timeout retry with a longer timeout or report back uncommitted; no plumbing, no temporary `GIT_INDEX_FILE`; before any push run `git diff --stat HEAD~1 HEAD` and confirm it touches only your files.
- Saved as built-in memory rule `feedback_no_git_plumbing_commits.md`; board warning posted the same night.

## Open questions and follow-ups
- Whether a pre-push hook should refuse a commit whose deletion count exceeds a threshold — not proposed to the user yet.
