# The diary is a status board, not a complete index of published artifacts

## Key conclusion

Asked to find every published page about one topic **from the diary**, the diary alone would have
returned half of them. Of the four pages in the bush-hiding family, two left no trace: one was
published on a day with **no diary file at all**, and another's republish wrote no row. The diary
also records an artifact's URL only occasionally — a grep for `claude.ai/code/artifact` across
every diary file returns two lines, for a project that has published thirty.

The diary is reliable for what it was built for: a single-glance board of what parallel sessions are
doing right now. It is **not** a complete historical index, and a question of the form "find all X we
have published" must be answered by cross-checking at least three sources.

## Evidence, measurements, facts

- The four bush-hiding pages and their diary coverage:
  - "What the environment does to hiding" (2026-08-21) — **no `docs/diary/2026-08-21.md` exists**.
  - "What makes this agent hide?" (2026-08-26) — the 08-26 diary has three sub-agent review rows and
    no row for the republish.
  - "The Sensor Ladder" (2026-09-04) — well covered across five diary days.
  - "Analysis Pipeline Layout" (2026-09-04) — covered.
- `grep -rn "claude.ai/code/artifact" docs/diary/` returns **2 hits** total, both from September.
  `Artifact action:"list"` returns 30 published artifacts for the account.
- The three sources that together give a complete answer:
  1. `Artifact action:"list"` — the authoritative set of what exists, with URLs and update dates.
  2. `grep -rn "Shareable page:" docs/ scripts/` — maps each URL back to the doc that owns it.
     Every project artifact doc carries this line as its first or second line, which makes it a
     reliable join key.
  3. `git log --format="%ad %h %s" -- <file>` on each page — gives the real revision history,
     which the diary does not carry.
- Cause is structural, not negligence: the diary protocol fires on *events an agent reports*
  (implemented / verified / insight / training). A publish is only logged if the session remembers
  to call `/diary`, and until today's change routing every publish through the `publish-page`
  skill there was nothing making that automatic.

## Decisions and actions

- **Practice**: when asked to inventory published work, start from `Artifact action:"list"`, join
  to owning docs with the `Shareable page:` grep, and use the diary for *narrative* (what happened,
  what was corrected) rather than for *coverage*.
- The `publish-page` skill's Step 5 now makes the diary call part of the publish flow, which should
  reduce future gaps — but it does not backfill the existing ones, so the cross-check stays necessary
  for anything published before 2026-09-09.
- Related, same layer: [[20260509_0311_diary_auto_session_backfill]] — the diary's auto-created
  session rows, which is why several days show "(auto — session-start was not called)".

## Open questions and follow-ups

- Whether to backfill the missing artifact rows for 2026-08-21 and 2026-08-26. The 08-21 case needs
  a diary file created for a past date, which the helper supports via `--date`, but writing history
  after the fact has its own risks and was not done.
- Whether an artifact's URL should be a required field in the diary row for a publish event, so the
  grep over diary files becomes a usable index in its own right.
