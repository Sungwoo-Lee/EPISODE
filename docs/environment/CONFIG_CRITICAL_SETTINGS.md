# Critical Config Settings & Change Log

**Purpose:** prevent silent config drift. Two parts below — a **registry** of high-impact settings (canonical value + meaning) and a dated **change log**. Rule: change a registry value → add a change-log entry in the **same commit** (missing entry = regression). Config-system mechanics: [CONFIG_GUIDE.md](CONFIG_GUIDE.md). Ground truth for a run's value = its saved `models/config.yaml`, not the source.

## Registry

Canonical value = what a config inheriting `configs/environment/default.yaml` resolves to. Changing a value in `default.yaml` changes every config that inherits it (training **and** probes) unless that config overrides the key.

| Setting (path) | Value | Set in | Meaning |
|---|---|---|---|
| `sensory.decay_power` | **1.0** | `default.yaml` | Olfactory distance falloff: smell = `1/dist^p` (cap 2.0 on-cell; `src/environment/sensor.py`). `1.0` = gentle, long-range gradient (predictive); `2.0` = inverse-square, ~1–2 cell reach. |
| `sensory.sensor_radius` | 20 | `default.yaml` | Max cells the olfactory sensor reaches at all. |
| `sensory.vector_size` | 5 | `default.yaml` | Olfactory channel width — part of `obs_dim`; changing it breaks checkpoint compatibility. |
| `body.death_penalty` | 100 | `default.yaml` | Terminal death penalty; large vs per-step reward → risk sensitivity. |
| `sensory.olfactory_grid_range` | **1** | `default.yaml` | Radius of the olfactory sampling diamond. `0` = pre-DIRECTIONAL_SENSORS single sample (byte-identical). `>0` adds `(2r²+2r+1)×vector_size` dims — **changes `obs_dim`, breaking checkpoint compatibility**. At the canonical `1` the agent smells a five-cell diamond, so the *direction* of a smell is available as a between-cell difference rather than only its strength. This is the half of the default sensory pair that carries IDENTITY: predator `[0, 0.7, 0.5, 0, 0]` against neutral `[0, 0.5, 0.7, 0, 0]`, separable only by ratio. |
| `sensory.visual_blur_enabled` | **true** | `default.yaml` | Anisotropic point-spread on vision (`sensory.visual_blur_anisotropy` 3.0). Changes observation *semantics* at identical width — in the modality fingerprint. **Blur is what makes `visual_value_mode: clamp` non-binary**: a single entity spreads to roughly 0.64 on its own cell and never reaches the 1.0 cap, so the cap binds only when two or more entities share a cell. Inherited from the sensor ladder's V-family and never varied *within* the single-channel condition — a candidate for the first sweep, not a measured optimum. |
| `sensory.visual_value_mode` | **clamp** | `default.yaml` | How per-entity visual mass is combined in a cell. **Both modes sum over entities first**; `clamp` then caps the total at 1.0 (`sensor.py:392-397`). Calling `clamp` a "presence" sensor is therefore only half right and the wording has misled once already: with blur on, the cap rarely binds, so what the agent receives is a **presence-capped blurred density** — graded, weakly count-sensitive until the sum passes 1.0, and **not bounded by `visual_sensor_range`**, which limits the cells SAMPLED, not the entities whose mass reaches them. Semantics at identical width; fingerprinted. |
| `sensory.visual_sensor_range` | **2** | `default.yaml` | Radius of the visual sampling diamond, in Manhattan cells, and therefore the WIDTH sight costs: `(2r² + 2r + 1) × visual_vector_size` dims. `0` = blind (the pre-2026-09-21 default), `1` = 5 cells, `2` = 13. **Changes `obs_dim`.** Pinned to **1** on `basic/00-static_predator_5x5.yaml` and `basic/01-slow_predator_5x5.yaml`: a radius-2 diamond on a 5-cell-wide map sees most of the world and stops being a local sensor. It bounds the cells sampled, **not** the entities contributing mass to them — an entity outside the diamond still leaks attenuated blur into it. |
| `sensory.visual_vector_size` | **1** | `default.yaml` | Width of every per-entity `visual_properties` vector. At the canonical `1` every entity — food, predator, rabbit, bush, rock, campfire — collapses to the same `[1.0]`, so vision reports THAT a cell is occupied and never WHAT occupies it; identity moves to olfaction. **Changes `obs_dim`** and is in the curriculum modality fingerprint. The loader enforces `len(visual_properties) == visual_vector_size` on every resource, entity and obstacle, so a config redeclaring one of those lists at a stale width fails at load rather than training on silent garbage. The 8-channel originals are preserved under `configs/environment/experiment/archive/basic_vec8/`. |
| `sensory.visual_occlusion_enabled` | **false** | `default.yaml` | Line-of-sight occlusion. Aggressive on this dense scene — see the calibration table in `02_config_schema.md`. Fingerprinted. |
| `thermal.enabled` | **false** | `default.yaml` | Master gate for the body-temperature system. Mandatory in every full config, **no fallback default** — a misspelled `thermal:` block must fail at load, not train as if thermal were off. False = the field is never built and the world is byte-identical to the pre-thermal environment. |
| `thermal.sigma` | **0.7** | `default.yaml` | Width, in cells, of the one Gaussian blur applied to the raw temperature field. It is what turns a single hot cell into a lethal centre with a survivable ring one cell out. Tight band 0.6–0.8: much larger and the fire blurs flat (no pain anywhere), much smaller and there is no warm ring at all. Validated `> 0`; read only when `thermal.enabled`. |
| `thermal.min_fire_separation` | **4** | `default.yaml` | Minimum Manhattan distance between two heat sources, in cells. Adjacent fires **add** their stamps, and the merged field is lethal exactly where the agent needs to stand: at separation 1 the comfort ring sits at +33.0 and at separation 2 at +15.4, both past the +15 death threshold, while at 3 it is +8.4 — the single-fire value. Below 3, an episode can have **no survivable position near the fire at all** and still look healthy in every metric. `0` = disabled (accepts merged fires) and is the only value that leaves the placement graph unchanged. Read only when `thermal.enabled`. **The +33.0 / +15.4 / +8.4 figures above were measured at `k_loss: 0.01` and have shifted**; the canonical value moved 3 → 4 on 2026-09-19 because at separation 3 two fires still merged enough that stepping onto a fire from the ring beside it crossed the heat-death threshold on the first step in some episodes (worst case +16.3). See that date's change-log entry for the 600-reset measurements behind the current value. |
| `thermal.k_loss` | **0.02** | `default.yaml` | Per-step fraction of the body's deviation from `thermal.temperature_setpoint` that physiology undoes — the body pulling back against the world. Together with `thermal.k_exchange` (0.04) it fixes the equilibrium `T* = k_exchange·T_field/(k_exchange + k_loss)`, which at the canonical **0.02** is `0.667·T_field` — so a −30 cell settles the body at −20 rather than −30 and the world's cold baseline is survivable. (At the pre-2026-09-19 `0.01` this factor was `0.8`; every radial-profile number measured before that date is stale, including the ring figures quoted in the `thermal.min_fire_separation` row below.) **This is the number most likely to be changed by accident**: at roughly `k_loss = 0.036` the survivable ambient window reaches ±25, the world's own baseline can no longer kill anything, and the thermal task quietly disappears while the config still looks configured. Validated `>= 0` and `k_exchange + k_loss <= 1` (above 1 the discrete update overshoots its own fixed point every step). Read only when `thermal.enabled`. |
| `thermal.warming_rate_scale` / `thermal.cooling_rate_scale` | **2.0 / 0.25** | `default.yaml` | Separate warming and cooling speeds. Each multiplies the body's **whole** per-step temperature change `d` (`warming_rate_scale` when `d > 0`, `cooling_rate_scale` otherwise), so every settling temperature is unchanged and only the time to reach it moves. **1.0 / 1.0 is byte-identical to the single-rate body** (a static gate; the scaled branch is not compiled) — but that is no longer the canonical value: since 2026-09-19 it is **2.0 / 0.25**, an 8× asymmetry past the commonly reported physiological range, recorded there as a deliberate model choice made to hit the user's survival targets (survive 80–110 steps away from a fire, rewarm from near-death in ≤10). Equal values other than 1.0 are a uniform slow-down and **not** today's behaviour. "Warming" follows the step's direction, so a warming scale above 1 also makes the fire kill sooner (and a cooling scale below 1 slows recovery from overheating). Validated `> 0` and `scale·(k_exchange + k_loss) <= 1` per key. The metabolic-coupling drain is deliberately **not** scaled. A documented deviation from EVAAA (single rate). The ecological rate-asymmetry figures behind the idea are unverified; `research-postdoc` should check them before any paper claim. Read only when `thermal.enabled`. Plan: [[warming_cooling_rate_scales]]. |
| `thermal.grid_range` | **1** | `default.yaml` | Radius of the thermoceptive Manhattan diamond, and therefore the WIDTH the sense costs: `2r² + 2r + 1` observation dimensions, so `1` = 5 dims and `2` = 13. Read only when `thermal.enabled`, validated `>= 0`. It is a static field, so changing it recompiles — and, far more importantly, it is **architecture-visible**: a checkpoint trained at one `grid_range` cannot be restored into another, and the curriculum pre-flight check rejects any schedule whose stages disagree on it (a curriculum is thermal throughout or non-thermal throughout). `1` is the design's value: the comfort ring sits at Manhattan distance 1 from a fire, so a radius-1 diamond is exactly what lets the agent identify a fire from the safest cell adjacent to it without stepping on it. |
| `thermal.relative` | **true** | `default.yaml` | `true` reports `thermal_field[cell] − body_temp` ("how much warmer than me"); `false` reports the raw field. Same width either way, different meaning — which is why it is in the curriculum modality fingerprint alongside `visual_value_mode`. Read only when `thermal.enabled`. |
| `thermal.body_temp_observable` | **true** | `default.yaml` | Does the agent receive its OWN body temperature as an observation? Every thermoceptor reading is a *difference* (`field − body_temp`), including the centre cell, so with this `false` the body's temperature is **latent**: recoverable only by integrating the recurrence over the whole episode. `true` delivers it directly as one extra dim, in **raw degrees**, immediately after Satiation. It is architecture-visible for the same reason `thermal.grid_range` is — it **changes `obs_dim`** (32 → 33 on the campfire example config), so a checkpoint trained on one side cannot be restored into the other and the curriculum pre-flight check rejects any schedule whose stages disagree on it. Static, in the modality fingerprint, and read only when `thermal.enabled`. It is the switch the "given vs. inferred body temperature" ablation flips, which is why both arms ship as separate configs (`experiment/thermal/campfire_world.yaml` and `..._body_temp_hidden.yaml`) rather than as an edit of one. |
| `thermal.max_temperature` | **15.0** | `default.yaml` | Two jobs, and the second one is easy to miss. (1) The upper end of the survivable body-temperature band — leaving `[min_temperature, max_temperature]` ends the episode with code 5. (2) **From Stage 4 it is also the warmth-vs-hunger exchange rate.** The homeostatic drive's third axis is `(T − temperature_setpoint) · max_satiation / max_temperature`, in satiation units, so at the shipped `max_satiation: 100` one degree of thermal deviation costs the same drive as **6.67** satiation units. Halving it does not merely narrow the band — it **doubles** the reward for staying warm, silently, with no other config key showing the change. Read only when `thermal.enabled`; validated `min_temperature < max_temperature`. |
| `environment.obstacles[bush].blocks_animals` | **true** | `default.yaml` | Is a bush a physical barrier to ANIMALS, or only concealment? `true` = an animal (predator or prey) cannot step onto the cell; the **agent still can**, which is the whole point — the bush becomes a refuge an animal cannot follow you into, not merely a place a hunter loses track of you. Merged into the animal movement mask only: `obs_block_for_animals = params.obs_blocking | params.obs_blocks_animals` (`core.py:560`), passed to `_hunt_step` and `_wander_step`. It is **not** in any placement validity mask — neither `resolve_overlaps_global` nor `relocate_blocked_entities` reads it (nor `obs_blocking`) — so it does not make the open "entity parked at (0,0) when its spawn area is full" bug more reachable, and animals may still *spawn* on a blocking bush. `move_agent` takes `obs_blocking`, not the merged array, so the agent's own movement is untouched: that asymmetry IS the feature. **Deliberate exception to the no-fallback-defaults rule** — read as `o.get('blocks_animals', False)` (`config_loader.py:1851`), so any config that redeclares its own `obstacles:` list and omits the key silently gets `false`. See the 2026-09-14 change-log entry for why the fallback is kept. |
| `body.recovery_in_bush_multiplier` | **1.0** | `default.yaml` | How much faster does a resting agent heal **while standing on a concealing bush** (an active obstacle with `hides_agent: true`)? It multiplies `recovery_amount` in `core.py::update_body`, i.e. it sits **inside** the existing rest-and-no-damage condition, so a premium is only collected on a step that would have healed something anyway. `1.0` = no difference from resting in the open, and it is the value every world in the tree ships. **Static field** (`struct.field(pytree_node=False)`), unlike its two `recovery_*` siblings, so the gate is a **trace-time Python `if`**: at exactly `1.0` the branch emits no operation and the environment's graph is character-for-character the pre-feature one — bit-parity with every earlier run is a property of the source, not a measurement. Read with `get_mandatory` + `float()` (the coercion matters: a static field is part of JAX's trace-cache key, so YAML `1` and `1.0` would be two cache entries) and validated `> 0`. **`rest_streak` is deliberately NOT location-dependent** (decision D2): a streak banked resting in the open is still worth what it was worth, because a location term would move survival for every config including those sitting at `1.0`. |

## Change log (newest first)

Entry = **date — `setting` old→new — reason — commit — blast radius.**

- **2026-09-21 — four new `sensory:` keys, display-only: `olfactory_channel_names`, `olfactory_channel_groups`, `visual_channel_names`, `visual_channel_groups`** — **Reason:** the names the episode video prints under each sensor channel's map ("Food", "Predator", "Terrain") were a hardcoded table inside the renderer's own source. They move into the config so a channel can be renamed by editing YAML, and the code tables are **deleted** rather than deprecated, so a name has exactly one source. A name that exists in two places can disagree with itself, and this renderer already lost that bet once on a *count* (`4b6f7196`, every video failed to render); a display name that disagrees with the channel it labels is worse, because nothing crashes. **Blast radius: VIDEO ONLY.** These keys are read at recording-write time by `eval_recording.channel_display_from_config`, never by `load_env_params`, so they touch no observation, no agent input and no training. Measured: the byte-parity gates are unchanged at 46 passed / 353 skipped before and after, and all eleven standalone env configs resolve to identical `EnvParams`. **Deliberately NOT added to the registry table above** — that table is for settings that change what a run *does*, and these change only what a video *says*. **No fallback defaults:** a missing key on an *enabled* sense raises `ValueError` naming the key; a sense's keys are read only when that sense resolves enabled, so a vision-off config needs no vision names. **Known cost, accepted by the user:** a checkpoint trained before this change cannot be re-recorded until [[SAVED_RUN_CONFIG_COMPAT]] lands, because its frozen saved config has no `extends:` and cannot carry keys invented after it finished. — `DASHBOARD_CHANNEL_NAMES_FROM_CONFIG.md`

- **2026-09-21 — the default sensory configuration becomes the sensor ladder's `Q2_presence_binary` arm: `sensory.olfactory_grid_range` 0 → 1, `visual_sensor_range` 0 → 2, `visual_vector_size` 8 → 1, `visual_value_mode` `sum` → `clamp`, `visual_blur_enabled` false → true (all in `configs/environment/default.yaml`), with `visual_sensor_range: 1` pinned on `basic/00-static_predator_5x5.yaml` and `basic/01-slow_predator_5x5.yaml`** — **Why:** the sensor-ladder study (14 arms, 1,000,000 evaluation episodes each) found that whether an agent responds to a *harmless* animal is set by one property: whether its sight can resolve **what** it is looking at. All nine arms whose vision carries eight appearance channels show a **negative** response to a nearby rabbit — they solved identity visually and stopped using smell. All five that cannot resolve identity show a **positive** one. `Q2_presence_binary` (olf 1, vis 2, vec 1, clamp) is the strongest of those with a real visual field: **+5.96 pp** response to a harmless animal, against a ~1.4 pp spread across five seeds of one configuration, so the effect is separable from seed noise. `B_olf_only` is higher still (+7.65) but is blind. **What the pair of settings buys, and it is the point of the choice:** at `visual_vector_size: 1` every entity collapses to the same number, so vision reports THAT something is at a cell and never WHAT — **though "presence" overstates it, and the overstatement was caught by `env-config-reviewer` at pre-flight on 2026-09-21 rather than by the sweep that produced it**: `sum` and `clamp` BOTH sum over entities first and `clamp` only caps the total at 1.0, so with blur on a lone entity reads about 0.64 on its own cell, two entities read more than one until the sum passes 1.0, and an entity outside `visual_sensor_range` still leaks attenuated mass inward. What the agent actually receives is a **presence-capped blurred density** whose per-entity value is identity-free. The identity claim holds; the binary and local claims do not. This is key-for-key identical to the archived `Q2_presence_binary` ladder arm, so the default reproduces the measured condition exactly — only the description was wrong — identity does not leave the world, it moves to the nose, since the two odour channels are `[0, 0.7, 0.5, 0, 0]` for a predator and `[0, 0.5, 0.7, 0, 0]` for a neutral and the **ratio** separates the classes. The default agent therefore has two modalities doing different jobs (vision = where, olfaction = what) and must combine them; Q2 demonstrably does not, which is a specific failure to fuse rather than general incompetence. **Blast radius — the observation width changes for every config that does not override it: 27 → 52** (olfaction 5 → 25, visual 8 → 13), and **44** on the two 5×5 levels, which pin `visual_sensor_range: 1` because a radius-2 diamond on a 5-cell-wide map sees most of the world and would stop being a local sensor. Seven basic levels resolve to olf 1 / vis 2 / vec 1 / clamp / blur on; `00` and `01` to olf 1 / vis 1 / vec 1 / clamp / blur on. **The 326 configs under `experiment/archive/` pin these keys explicitly and are untouched**, so the sensor-ladder arms and every neuromodulator grid cell remain reproducible. **`visual_vector_size` and `visual_blur_enabled` are fingerprinted by the curriculum modality check** (`train.py`, `dreamer_srl_main.py`), so a run cannot resume across this change and a curriculum cannot span `00`/`01` (44 dims) and `02`–`06` (52 dims) — both are the check working, not a defect. **Every agent trained before this line learned a different observation space; policies and survival numbers are not comparable across it.** **Two settings are inherited rather than measured, and are named here so they are not mistaken for findings:** `visual_blur_enabled: true` with `visual_blur_anisotropy: 3.0` came to `Q2` from the V-family and was never varied *within* the single-channel condition — a candidate for the first sweep; and the ranking among the four non-resolving arms (+0.75 to +0.39 on the stricter injury-driven hypervigilance measure) is **not** separable from seed noise, whose spread on that measure is 1.05–2.67 pp across five seeds — only the group split (5 positive, 9 negative, 14 of 14) is supported. **Files also moved in this change:** `basic/03-random_init_10x10_ckpt1k.yaml` → `experiment/archive/basic_superseded/` (a checkpoint-frequency variant, not a world), and `basic/05-campfire_thermal_10x10_olf1_vis2.yaml` and `..._olf1_vis3.yaml` deleted — the first became byte-equivalent to its parent under the new default, the second differed only in `visual_sensor_range: 3`; neither was referenced anywhere outside itself. The basic set is now seven levels, `00`–`06`.

- **2026-09-19 — the thermal world is retuned to the user's survival targets: `thermal.default_temp` [-28,-22] → [-31,-29], `thermal.k_loss` 0.01 → 0.02, `thermal.warming_rate_scale` 1.0 → 2.0, `thermal.cooling_rate_scale` 1.0 → 0.25, `thermal.min_fire_separation` 3 → 4 (all in `configs/environment/default.yaml`), and `temperature_ratio` [11,13] → [11,11] on the campfire in `configs/environment/experiment/basic/05-campfire_thermal_10x10.yaml`** — the first world that turns temperature on. **Why:** the user set three behavioural targets — survive 80–110 steps away from a fire (matching the 100-step hunger clock, since the agent must also forage, avoid predators and heal), rewarm from near-death in ≤10 steps (a predator strikes within 1–3 steps of arriving), and die on the fire cell by step 2–3 with the first step survivable. At the previous values the agent survived only ~34 steps away, rewarmed in ~20, and a search of ~120,000 combinations of the pre-existing keys found **zero** settings meeting the away and rewarm targets together: one rate cannot make cooling slow and warming fast. The warming/cooling scales (commit `d4c30a2a`) made it reachable; the remaining changes remove the per-episode variation that made it unreachable *in every episode*. **Measured on 600 real resets of level 05 through the live loader and reset path** (not a closed form): away 86–99 steps, rewarm 9–10, first step from the ring onto the fire +10.9..+12.3 (death at +15), death on the fire at step 2, 0 episodes without a survivable cell, 16.1 survivable cells per episode, 0 fires parked outside their spawn area. **Two consequences to know:** (a) doubling `k_loss` **moves every equilibrium** — unlike the rate scales, which leave the map untouched — so the radial profile the design page was tuned on has shifted and any figure quoting +8.09 for the ring is stale; (b) the narrowed `default_temp` and the fixed `temperature_ratio` **remove most episode-to-episode variation in the thermal world**, which is a deliberate loss of scene diversity. **`min_fire_separation` 3 → 4 is load-bearing**: with up to three fires, two fires three cells apart merge enough that stepping onto the fire from the ring beside it crossed the heat-death threshold on the first step in some episodes (worst case +16.3) — the failure that a single-fire calculation missed and a live sweep caught. Warming 2.0 against cooling 0.25 is an 8× asymmetry, past the commonly reported physiological range; recorded as a deliberate model choice, and the literature figures are still unverified (→ `research-postdoc`). Follow-up detail and the rejected alternatives are in [[WARMING_COOLING_RATE_SCALES]].

- **2026-09-17 — new conditional-mandatory keys `thermal.warming_rate_scale` and `thermal.cooling_rate_scale`, shipped at 1.0 / 1.0 (separate warming and cooling speeds)** — **Reason:** the user's behavioural targets for body temperature — about 80–110 steps to freeze away from a fire, a rewarm from near-death in 10 steps or fewer, and death on the fire itself by step 2–3 — were infeasible together: a search of about 120,000 single-rate settings found none that meets the away and rewarm targets at once, because one speed cannot be slow for cooling and fast for warming. **Design:** each key multiplies the body's **whole** per-step change `d = k_exchange·(T_field − T) + k_metabolic − k_loss·(T − temperature_setpoint)` — `warming_rate_scale` when `d > 0`, `cooling_rate_scale` otherwise. Scaling the whole step, rather than `k_exchange`, leaves every settling temperature exactly where it was, so the load-time structure check is untouched. Both are static `EnvParams` fields and `core.py::update_body` gates on `== 1.0` for both at trace time, so at 1.0 / 1.0 the scaled branch contributes no operation to the graph. **Measured, not argued:** the `jax_step` jaxpr SHA-1 at 1.0 / 1.0 is identical before and after on `default.yaml` (`a3a2f04f`), the archived `campfire_world.yaml` (`ef1b0a1f`) and `basic/05-campfire_thermal_10x10.yaml` (`188186e9`), and differs on both thermal-on configs when a scale is set to 3.0 (the contrast case). A new fixture `tests/env/fixtures/thermal_rate_scales/single_rate_rollouts.npz`, captured from a worktree of the pre-change tip in commit `068d791e`, holds four warming and cooling rollouts; it is byte-identical at 1.0 / 1.0. It was needed because the older thermal-on fixture never warms (0 warming steps in 300). Every byte-parity family is unchanged, run file by file on CPU: `thermal_parity` 12 passed / 21 skipped, `parity` 34 passed / 325 skipped, `visual_parity` 8 passed, `extero_noc_parity` 3 passed, `metabolic_coupling` 11 passed. `tests/env/test_thermal_rate_scales.py` (14 tests) pins the rest. **Semantics that bite:** "warming" follows the direction of the step, so a warming scale above 1 also makes the fire kill sooner, and a cooling scale below 1 also slows recovery from overheating. Equal values other than 1.0 are a uniform slow-down, not today's behaviour. Validated `> 0` (NaN refused) and `scale·(k_exchange + k_loss) <= 1` per key; the existing `k_exchange + k_loss <= 1` check is kept. **Deviation from EVAAA:** EVAAA updates body temperature with one coefficient (`vendor/evaaa/evaaa_unity/Assets/Scripts/Agent/InteroceptiveAgent.cs:860-878`); two rates are a deliberate departure. **Ecology:** faster heating than cooling is plausible in kind (ectotherm cardiovascular control; endotherm vasomotor asymmetry), but the 4–6× ratio the targets probably need is a model choice, and the literature figures are unverified — `research-postdoc` should check them before any paper claim. **Drain not scaled:** the `metabolic_coupling` bill stays `rate·|k_loss·(T − setpoint)|` on the pre-step temperature. A bill scaled by the step's direction would be path-dependent or jittery at a settled body temperature, where that direction is decided by float rounding. This is defensible but not the only choice: the time-dilation reading (bill × scale) and a switch on the defence direction `sign(setpoint − T)` are both deferred to OPEN_WORK_HANDOFF E1(a). **Migration:** the keys are written inline at 1.0 / 1.0 in `default.yaml` and the two archived thermal-on worlds (`campfire_world.yaml`, `campfire_world_body_temp_hidden.yaml`, which eight test modules and a fixture generator load from a raw `Config`). `basic/05` and `basic/06` inherit them; verified through `load_env_config` → `load_env_params`, where all four thermal-on configs resolve to float 1.0 / 1.0. **Load counts, before → after**, population = tracked `configs/environment/**/*.yaml` (335 files), standalone = no `extends:` key: standalone 118 with 27 loading → 118 / 27; layered 217 with 211 loading → 217 / 211; identical per file. This population differs from the 2026-09-16 figures (whole `configs/` tree), so the two sets of numbers must not be compared. **Saved runs affected:** 0 of 503 (no saved `models/config.yaml` has `thermal.enabled: true`). **Commit:** fixture `068d791e`; the code, config and doc change is the plan's second commit, made after review. **Blast radius:** none at the shipped 1.0 / 1.0. Choosing values is a separate follow-up, which must evaluate the targets at the corners of the sampled world and fire-ratio ranges. Plan: [[warming_cooling_rate_scales]].
- **2026-09-15 — new mandatory key `body.recovery_in_bush_multiplier`, shipped at the inert `1.0`: resting inside a bush can heal faster than resting in the open (Part B2 of the bush-refuge plan)** — the bush already hides the agent and, since A1, physically blocks animals. ## Protocol & required reading

- **On any registry-value change:** add a same-commit change-log entry (date, path, old→new, reason, blast radius). A schema/system change also updates [CONFIG_GUIDE.md](CONFIG_GUIDE.md) + [02_config_schema.md](02_config_schema.md).
- **Required reading** (registry + change log, before config/launch work): `env-config-reviewer`, `experiment-designer`, `training-runner`, `developer`, `senior-developer`. They enforce the protocol — a registry change without an entry is a flagged regression.
