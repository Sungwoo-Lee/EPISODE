# Critical Config Settings & Change Log

**Purpose:** prevent silent config drift. Two parts below — a **registry** of high-impact settings (canonical value + meaning) and a dated **change log**. Rule: change a registry value → add a change-log entry in the **same commit** (missing entry = regression). Config-system mechanics: [CONFIG_GUIDE.md](CONFIG_GUIDE.md). Ground truth for a run's value = its saved `models/config.yaml`, not the source.

## Registry

Canonical value = what a config inheriting `configs/environment/default.yaml` resolves to. Changing a value in `default.yaml` changes every config that inherits it (training **and** probes) unless that config overrides the key.

Inherited from the sensor ladder's V-family and never varied *within* the single-channel condition — a candidate for the first sweep, not a measured optimum. |
| `sensory.visual_value_mode` | **clamp** | `default.yaml` | How per-entity visual mass is combined in a cell. **Both modes sum over entities first**; `clamp` then caps the total at 1.0 (`sensor.py:392-397`). Calling `clamp` a "presence" sensor is therefore only half right and the wording has misled once already: with blur on, the cap rarely binds, so what the agent receives is a **presence-capped blurred density** — graded, weakly count-sensitive until the sum passes 1.0, and **not bounded by `visual_sensor_range`**, which limits the cells SAMPLED, not the entities whose mass reaches them. Semantics at identical width; fingerprinted. |
| `sensory.visual_sensor_range` | **2** | `default.yaml` | Radius of the visual sampling diamond, in Manhattan cells, and therefore the WIDTH sight costs: `(2r² + 2r + 1) × visual_vector_size` dims. `0` = blind (the pre-2026-09-21 default), `1` = 5 cells, `2` = 13. **Changes `obs_dim`.** Pinned to **1** on `basic/00-static_predator_5x5.yaml` and `basic/01-slow_predator_5x5.yaml`: a radius-2 diamond on a 5-cell-wide map sees most of the world and stops being a local sensor. It bounds the cells sampled, **not** the entities contributing mass to them — an entity outside the diamond still leaks attenuated blur into it. |
| `sensory.visual_vector_size` | **1** | `default.yaml` | Width of every per-entity `visual_properties` vector. At the canonical `1` every entity — food, predator, rabbit, bush, rock, campfire — collapses to the same `[1.0]`, so vision reports THAT a cell is occupied and never WHAT occupies it; identity moves to olfaction. **Changes `obs_dim`** and is in the curriculum modality fingerprint. The loader enforces `len(visual_properties) == visual_vector_size` on every resource, entity and obstacle, so a config redeclaring one of those lists at a stale width fails at load rather than training on silent garbage. The 8-channel originals are preserved under `configs/environment/experiment/archive/basic_vec8/`. |
| `sensory.visual_occlusion_enabled` | **false** | `default.yaml` | Line-of-sight occlusion. Aggressive on this dense scene — see the calibration table in `02_config_schema.md`. Fingerprinted. |
| `thermal.enabled` | **false** | `default.yaml` | Master gate for the body-temperature system. Mandatory in every full config, **no fallback default** — a misspelled `thermal:` block must fail at load, not train as if thermal were off. False = the field is never built and the world is byte-identical to the pre-thermal environment. |
| `thermal.sigma` | **0.7** | `default.yaml` | Width, in cells, of the one Gaussian blur applied to the raw temperature field. It is what turns a single hot cell into a lethal centre with a survivable ring one cell out. Tight band 0.6–0.8: much larger and the fire blurs flat (no pain anywhere), much smaller and there is no warm ring at all. Validated `> 0`; read only when `thermal.enabled`. |
| `thermal.min_fire_separation` | **4** | `default.yaml` | Minimum Manhattan distance between two heat sources, in cells. Adjacent fires **add** their stamps, and the merged field is lethal exactly where the agent needs to stand: at separation 1 the comfort ring sits at +33.0 and at separation 2 at +15.4, both past the +15 death threshold, while at 3 it is +8.4 — the single-fire value. Below 3, an episode can have **no survivable position near the fire at all** and still look healthy in every metric. `0` = disabled (accepts merged fires) and is the only value that leaves the placement graph unchanged. Read only when `thermal.enabled`. **The +33.0 / +15.4 / +8.4 figures above were measured at `k_loss: 0.01` and have shifted**; the canonical value moved 3 → 4 on 2026-09-19 because at separation 3 two fires still merged enough that stepping onto a fire from the ring beside it crossed the heat-death threshold on the first step in some episodes (worst case +16.3). See that date's change-log entry for the 600-reset measurements behind the current value. |
| `thermal.k_loss` | **0.02** | `default.yaml` | Per-step fraction of the body's deviation from `thermal.temperature_setpoint` that physiology undoes — the body pulling back against the world. Together with `thermal.k_exchange` (0.04) it fixes the equilibrium `T* = k_exchange·T_field/(k_exchange + k_loss)`, which at the canonical **0.02** is `0.667·T_field` — so a −30 cell settles the body at −20 rather than −30 and the world's cold baseline is survivable. (At the pre-2026-09-19 `0.01` this factor was `0.8`; every radial-profile number measured before that date is stale, including the ring figures quoted in the `thermal.min_fire_separation` row below.) **This is the number most likely to be changed by accident**: at roughly `k_loss = 0.036` the survivable ambient window reaches ±25, the world's own baseline can no longer kill anything, and the thermal task quietly disappears while the config still looks configured. Validated `>= 0` and `k_exchange + k_loss <= 1` (above 1 the discrete update overshoots its own fixed point every step). Read only when `thermal.enabled`. |
| `thermal.warming_rate_scale` / `thermal.cooling_rate_scale` | **2.0 / 0.25** | `default.yaml` | Separate warming and cooling speeds. Each multiplies the body's **whole** per-step temperature change `d` (`warming_rate_scale` when `d > 0`, `cooling_rate_scale` otherwise), so every settling temperature is unchanged and only the time to reach it moves. **1.0 / 1.0 is byte-identical to the single-rate body** (a static gate; the scaled branch is not compiled) — but that is no longer the canonical value: since 2026-09-19 it is **2.0 / 0.25**, an 8× asymmetry past the commonly reported physiological range, recorded there as a deliberate model choice made to hit the user's survival targets (survive 80–110 steps away from a fire, rewarm from near-death in ≤10). Equal values other than 1.0 are a uniform slow-down and **not** today's behaviour. "Warming" follows the step's direction, so a warming scale above 1 also makes the fire kill sooner (and a cooling scale below 1 slows recovery from overheating). Validated `> 0` and `scale·(k_exchange + k_loss) <= 1` per key. The metabolic-coupling drain is deliberately **not** scaled. A documented deviation from EVAAA (single rate). The ecological rate-asymmetry figures behind the idea are unverified; `research-postdoc` should check them before any paper claim. Read only when `thermal.enabled`. Plan: [[warming_cooling_rate_scales]]. |
| `thermal.grid_range` | **1** | `default.yaml` | Radius of the thermoceptive Manhattan diamond, and therefore the WIDTH the sense costs: `2r² + 2r + 1` observation dimensions, so `1` = 5 dims and `2` = 13. Read only when `thermal.enabled`, validated `>= 0`. It is a static field, so changing it recompiles — and, far more importantly, it is **architecture-visible**: a checkpoint trained at one `grid_range` cannot be restored into another, and the curriculum pre-flight check rejects any schedule whose stages disagree on it (a curriculum is thermal throughout or non-thermal throughout). `1` is the design's value: the comfort ring sits at Manhattan distance 1 from a fire, so a radius-1 diamond is exactly what lets the agent identify a fire from the safest cell adjacent to it without stepping on it. |
| `thermal.relative` | **true** | `default.yaml` | `true` reports `thermal_field[cell] − body_temp` ("how much warmer than me"); `false` reports the raw field. Same width either way, different meaning — which is why it is in the curriculum modality fingerprint alongside `visual_value_mode`. Read only when `thermal.enabled`. |
| `thermal.body_temp_observable` | **true** | `default.yaml` | Does the agent receive its OWN body temperature as an observation? Every thermoceptor reading is a *difference* (`field − body_temp`), including the centre cell, so with this `false` the body's temperature is **latent**: recoverable only by integrating the recurrence over the whole episode. `true` delivers it directly as one extra dim, in **raw degrees**, immediately after Satiation. It is architecture-visible for the same reason `thermal.grid_range` is — it **changes `obs_dim`** (32 → 33 on the campfire example config), so a checkpoint trained on one side cannot be restored into the other and the curriculum pre-flight check rejects any schedule whose stages disagree on it. Static, in the modality fingerprint, and read only when `thermal.enabled`. It is the switch the "given vs. inferred body temperature" ablation flips, which is why both arms ship as separate configs (`experiment/thermal/campfire_world.yaml` and `..._body_temp_hidden.yaml`) rather than as an edit of one. |
| `thermal.max_temperature` | **15.0** | `default.yaml` | Two jobs, and the second one is easy to miss. (1) The upper end of the survivable body-temperature band — leaving `[min_temperature, max_temperature]` ends the episode with code 5. (2) **From Stage 4 it is also the warmth-vs-hunger exchange rate.** The homeostatic drive's third axis is `(T − temperature_setpoint) · range_S / max_temperature`, in satiation units, where `range_S = max(satiation_setpoint, max_satiation − satiation_setpoint)` is the furthest satiation can get from its own target (`core.py::satiation_deviation_range`). At the shipped `range_S = 100` one degree of thermal deviation costs the same drive as **6.67** satiation units — the same factor as every thermal run to date. It reads `range_S` and **not** `max_satiation` precisely so that the 2026-09-22 ceiling change (100 → 200) could not silently double it to 13.33. Halving it does not merely narrow the band — it **doubles** the reward for staying warm, silently, with no other config key showing the change. Read only when `thermal.enabled`; validated `min_temperature < max_temperature`. |
| `environment.obstacles[bush].blocks_animals` | **true** | `default.yaml` | Is a bush a physical barrier to ANIMALS, or only concealment? `true` = an animal (predator or prey) cannot step onto the cell; the **agent still can**, which is the whole point — the bush becomes a refuge an animal cannot follow you into, not merely a place a hunter loses track of you. Merged into the animal movement mask only: `obs_block_for_animals = params.obs_blocking | params.obs_blocks_animals` (`core.py:560`), passed to `_hunt_step` and `_wander_step`. It is **not** in any placement validity mask — neither `resolve_overlaps_global` nor `relocate_blocked_entities` reads it (nor `obs_blocking`) — so it does not make the open "entity parked at (0,0) when its spawn area is full" bug more reachable, and animals may still *spawn* on a blocking bush. `move_agent` takes `obs_blocking`, not the merged array, so the agent's own movement is untouched: that asymmetry IS the feature. **Deliberate exception to the no-fallback-defaults rule** — read as `o.get('blocks_animals', False)` (`config_loader.py:1851`), so any config that redeclares its own `obstacles:` list and omits the key silently gets `false`. See the 2026-09-14 change-log entry for why the fallback is kept. |
| `body.max_nutrition` / `body.max_satiation` | **200 / 200** | `default.yaml` | The top of the food axis. **Since 2026-09-22 this is NOT the target** — `body.satiation_setpoint` sits at 100, the MIDDLE. Both must move together in practice: satiation is derived from nutrition as `max_satiation * (N/max_nutrition)^k`, so at the shipped `nutrition_to_satiation_scaling_factor: 1.0` and equal ceilings satiation IS nutrition, and a config that raised one without the other would silently rescale the other. `max_satiation` is also the **agent-facing normaliser**: the Satiation observation is `satiation / max_satiation` (`sensor.py:477`), so doubling the ceiling halves the number the agent reads at a given nutrition — same observation width, different meaning, and every policy trained before 2026-09-22 read the other one. |
| `body.satiation_setpoint` | **100** | `default.yaml` | The homeostatic target: the drive is the distance from `[setpoint, 0]` (`core.py::calculate_drive`), so the reward `prev_drive − curr_drive` pays for moving TOWARD this number from either side. Unchanged in value since forever, but its **meaning** changed on 2026-09-22: it used to equal `max_satiation`, i.e. the target was the ceiling, so more food was always better and the axis was one-sided. It is now the middle of `[0, 200]`, so eating past it is punished exactly as much as being equally hungry. **The derived quantity to know is `range_S = max(setpoint − 0, max_satiation − setpoint)`** (`core.py::satiation_deviation_range`) — the furthest the axis can get from target, 100 today. `range_S` and not `max_satiation` is the deviation scale used by the thermal drive axis and by the logged `drive_hunger`; the two coincide only while the setpoint is the ceiling. |
| `body.overeating_death` | **true** | `default.yaml` | Does too much food kill? Death at `nutrition >= max_nutrition`, symmetric with starvation at `nutrition <= 0`, folded into `done` inside `core.py::update_body` so the `death_penalty` fires and termination reason 3 is stamped on that step and no other. **Was a NO-OP from its introduction until 2026-09-22**: it set the reason code in `jax_step` and never touched `done`, so with the setpoint at the ceiling it labelled ordinary surviving steps "died of over-eating" (KNOWN_BUGS, "Env doc-audit latent findings", open 2026-06-09). Static field (`pytree_node=False`), so at `false` **the `done` block** emits no operation at all — measured: `update_body`'s jaxpr with the key off is the with-it-on equation list minus exactly the `>=` and the `where`, and nothing else moves (`tests/env/test_two_sided_nutrition.py`). The step graph **as a whole did grow** for every config, on or off, because `satiation_deviation_range` runs on the drive and diagnostic paths unconditionally: `code-reviewer` measured `jax_step` at 716 → 722 equations thermal-off and 771 → 781 thermal-on. What is preserved at a ceiling setpoint is the **arithmetic** — bit-identical, pinned by byte-parity tests — not the equation count. |
| `body.start_nutrition_high` | **200** | `default.yaml` | Upper bound of the uniform draw for a randomised start, read only when `body.random_start_nutrition` is true (conditional-mandatory). Validated `0 <= low <= high <= max_nutrition`. **`experiment/basic/03-random_init_10x10.yaml` pins its own copy of this key and levels 04–06 extend it** — those four are the only worlds in the tree that randomise nutrition at all. | `body.recovery_base_rate` | **0.2** | `default.yaml` | Injury points healed per rest step, before the streak and location terms. With `recovery_accel_rate: 0.0` this IS the open-ground healing rate, so 50 consecutive rest steps clear 10 points of the 100-point scale and 100 steps clear 20 — both under the 25-point threshold the tuning study set for "resting in the open is not worth doing". At the previous **0.1 with accel 0.5** the open cleared the ENTIRE scale in about 12 rest steps. **Changing this changes survival on every world.** |
| `body.recovery_accel_rate` | **0.0** | `default.yaml` | Compounding on a consecutive-rest streak: `base × (1 + accel)^(streak − 1)`. **0.0 = off, and off is load-bearing rather than a default nobody set** — no base rate survives a non-zero accel of any size worth having: at `base 0.2` the largest workable value is **0.033** on a 50-step rest budget and **0.004** on a 100-step one, against the **0.5** that shipped until 2026-09-22, one to two orders of magnitude above either. ## Protocol & required reading

- **On any registry-value change:** add a same-commit change-log entry (date, path, old→new, reason, blast radius). A schema/system change also updates [CONFIG_GUIDE.md](CONFIG_GUIDE.md) + [02_config_schema.md](02_config_schema.md).
- **Required reading** (registry + change log, before config/launch work): `env-config-reviewer`, `experiment-designer`, `training-runner`, `developer`, `senior-developer`. They enforce the protocol — a registry change without an entry is a flagged regression.
