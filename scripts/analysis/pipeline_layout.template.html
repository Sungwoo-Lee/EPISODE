Analysis Pipeline Layout

How a trajectory store becomes a published figure, one stage at a time — every script named by its real path, with the code that does the work. This describes the pipeline as it exists and runs today. As of 5 September 2026 that includes the shared scan: the three programs that each re-implemented the shard loop now run on one.

What this is

The project trains agents, records what they did into a store of Parquet files, and turns that into figures and a shareable page. The turning-into-figures half is what this page documents.

It runs in five stages, and the reason it is worth drawing is that the stages have very different shapes. One stage reads hundreds of gigabytes and takes minutes per arm. Three stages read a few megabytes of JSON and take seconds. Knowing which is which is most of what you need to work on this code without waiting on it: if you are changing how a figure looks, you never touch the slow stage.

Every path below is real and every code block is copied verbatim from the file it names, so you can open any of them and find what you see here.

This page has been wrong twice, in opposite directions

Its first version argued for reorganising this code. Its second version described the code as it stood and said the reorganisation was parked and unbuilt. On 5 September 2026 the refactor was resumed and completed, so this third version documents the shared scan as a thing that exists. If a claim here looks stale, the tree wins — every path, line count and excerpt below was read from it.

What was required before any of it shipped. Each ported sweep had to reproduce the pipeline it replaced, checked mechanically rather than by reading: integer fields bit-exact, floats inside a tolerance fixed before porting began. All three passed on all fourteen arms, and all fifteen figures came back byte-identical — then the originals were deleted and the figures were checked again, because "the port is complete" has to mean nothing downstream noticed.

The shape of it

The core, function by function

Four modules, {{LC:scripts/analysis/core/store.py}} + {{LC:scripts/analysis/core/scan.py}} + {{LC:scripts/analysis/core/env.py}} + {{LC:scripts/analysis/core/golden.py}} lines, that every analysis in the project goes through. They are worth reading in this order, because each one assumes the one before it.

Six words this section uses

Store — the recorded output of putting a trained agent back into its world for a million lives. Not code: files. Shard — one file of that store; the recording is split across hundreds so nothing has to be held in memory at once. Parquet — the file format they are in, which stores a table column by column, so reading three columns out of thirty costs a tenth of the time. Sweep — one complete pass over every shard of one agent's store. Aggregate — the small summary a sweep writes, in this project about 7 KB against the 452 GB it was computed from. Arm — one trained agent in a study; the sensor ladder has fourteen.

store.py — find the files, and refuse to proceed if they are not one population

A single agent's million episodes may have been recorded in more than one sitting, into more than one directory. open_run() takes those directories, finds every shard under them, and treats the lot as one population — which is only legitimate if the pieces actually join up. The check is on the episode seed, the number that picks which random world an episode gets: across the union of directories the seeds must run without a gap and without a repeat.

A gap means episodes are missing and the analysis will report a population it does not have. A repeat means some world was counted twice. Neither would raise on its own; both would produce a figure that looks entirely normal.

{{CODE:scripts/analysis/core/store.py#57-62}}

The rest of the module is small readers — episode() for a column of the per-episode table, episode_list() for a column that holds a list per episode, and episode_property(), which deserves its own note:

{{CODE:scripts/analysis/core/store.py#Store.episode_property}}

The shape of that array is not written down anywhere in the file, so it has to be inferred from the total number of values — and an inferred shape that happens to divide evenly is exactly how a silently transposed array reaches a figure. Hence the check rather than a bare reshape.

scan.py — the one loop, and what it hands the study

Three programs in this repository used to walk the shards, written months apart, each carrying whichever safety checks its author had in mind that day. Of the twenty applicable checks across them, ten were simply absent — and all three bugs this analysis has actually hit sat in an absent one. They now share this loop.

Frame wraps a single shard and works out, once, the things every study needs and most get wrong: where each episode starts, which rows are real steps, and which row a given decision was taken on.

{{CODE:scripts/analysis/core/scan.py#49-62}}

Then sweep() walks the shards, hands each Frame to the study's own function, and — the important part — counts the steps itself as it goes, so it can check the total against the episode table at the end. The study's code cannot fake that number, because the driver is not asking the study for it:

{{CODE:scripts/analysis/core/scan.py#sweep}}

Note what sweep() deliberately is not: it is a driver, not a language for describing measurements. An earlier design had studies declare what to count and never write a loop. That does not survive contact with what these sweeps do — crossed two-dimensional grids, per-episode-by-bin matrices, quantile-derived bin edges, a running convolution with a reset boundary. Either the language grows a dozen constructs, or the escape hatch becomes the normal path; and an abstraction everybody bypasses is worse than none.

env.py — facts about the world, read from the run's own saved config

Every measure needs to know things about the environment that are not in the trajectory files: which slot in the animal array is a predator and which a rabbit, which observation channels carry smell, how the agent's pain signal is built from its recent injuries. All of it is derived from the configuration file that the training run itself saved, so an analysis reads the world the agent actually lived in rather than today's defaults.

This module exists because those derivations were copied into eleven places and had all drifted. They were merged only after proving the variants agreed on all fourteen agents and on 870,172 real step rows.

{{CODE:scripts/analysis/core/env.py#perceived_nociception}}

That one is worth reading closely even if you skip the rest: the agent does not feel its wound directly. It feels a weighted average of the last twelve steps of damage, which means an agent that wakes badly hurt feels nothing for the first two steps and does not feel the full wound until about step twelve. Several published findings on this project turn on that delay, and binning behaviour by the injury level rather than by the felt signal measures a quantity the agent cannot sense.

golden.py — how the rewrite was allowed to ship

When the three loops were merged into one, the question was not “does the new code look right” but “does it produce the same numbers”. Every ported sweep wrote to a scratch directory and was compared, field by field, against a snapshot of the old pipeline's output taken beforehand.

The comparison is tiered, and the tiers were fixed before any porting started: anything that is a whole number — a count, a sum of zeros and ones — must match exactly; anything else must match to twelve decimal places. Which tier a field is in is decided mechanically, by whether its values are whole numbers on both sides, so the gate cannot be relaxed after the fact by reclassifying a field that failed.

{{CODE:scripts/analysis/core/golden.py#_is_intlike}}

One further guard is easy to miss and does real work: a field that is a whole number in the old output and not in the new one is reported as a tier break, not quietly demoted to the looser comparison. A count that has grown a fractional part is wrong however small the difference.

Stage by stage

1 · The store — the input, not code

results/trajectories_lad/  +  results/trajectories_lad2/

452 GB · 3.32 billion step rows · 14 million episodes · read-only to everything below

Sharded Parquet, written once by the collector and never modified by the analysis layer. Two directories because the population was collected in two passes; each shard directory carries a _manifest.json recording every parameter the collection used, which is what made it possible to reconstruct the collection specs after the fact.

Nothing on this page writes here. If an analysis is wrong, re-running it costs minutes; the store is not at risk.

2 · The scan — one loop, every guard, for all three sweeps

scripts/analysis/core/store.py  ·  107 lines  |  scripts/analysis/core/scan.py  ·  119 lines

the only code that opens the store · asserts what must be true of it

Until 5 September 2026 there were three shard loops here, written months apart, each carrying a different subset of the same safety checks. Of twenty applicable check-cells across them, ten were empty — and all three bugs this analysis has actually hit sat in an empty cell. None of them raised. A third of episodes with no predator filed into the comparison group, a rebuild running on stale data, and a dose-response reading its predictor from the wrong row all produced figures that looked entirely fine.

Both of those guards are set out in full in the core, function by function above. What belongs here is the distinction that section draws, because it is the whole design:

Asserts are properties of the data — shard alignment, seed contiguity, the step-count cross-check. They cannot be bypassed and they cannot move a number: they either pass or they fire. Provisions are conventions — is_step, prev, initial. A callback is free to ignore them and index the raw arrays, so the guarantee they offer is auditable rather than structural. frame.raw() is the deliberately conspicuous way to do that, and the plan counts its uses per sweep so a port that starts bypassing the driver becomes visible.

scripts/analysis/studies/sensor_ladder/collect_arm_data.py  ·  185 lines

one arm’s store → results/analysis/ladder/<arm>.json · ~60 s per arm

A study now supplies only its own arithmetic. The callback is ordinary NumPy in the study’s own folder, and the bookkeeping it used to carry is gone:

{{CODE:scripts/analysis/studies/sensor_ladder/collect_arm_data.py#102-113}}

Two conventions here are preserved rather than tidied, because tidying them would move published numbers: bush steps exclude the reset row while damage and eating include it — both forms are asked for explicitly at the call site rather than hidden in one default — and the odour quartile edges come from the first shard only.

…/collect_time_course.py  ·  99 lines  |  …/collect_hiding_drivers.py  ·  157 lines

the step-by-step sweep, and the episode-level regressions

The time-course sweep asks a different shape of question — what happened at step t, averaged over episodes — and reconstructs the agent’s felt nociception, which the store never records. The factor sweep fits regressions and so needs one row per episode.

The factor sweep does not replace scripts/analysis/hiding_drivers.py (387 lines), which stays: the earlier study’s README names it as that study’s producer, and lad06 decides which arms to draw by checking whether its CSV exists. It also reproduces that script’s contemporaneous injury binning bug-for-bug — every other predictor in this analysis comes from the previous row, that one does not, and it feeds published cross-tabs. Correcting it inside a refactor would move a published number under cover of a cleanup, so it is registered as its own adjudicated change instead.

scripts/analysis/core/env.py  ·  96 lines

everything derived from a run’s saved config

Five helpers that existed in three copies each. Every copy had drifted textually, which sounds alarming until you ask the question that decides whether merging is safe, which is behavioural:

Three were safe to merge as written. slot_layout genuinely differed — and the difference is the kind that looks alarming and is not: all three agree on every slot list any caller reads, and differ only in whether they also return three convenience counts. So core returns the superset, which is safe only because no caller iterates the dict. That was checked across all four call sites rather than assumed; a caller that iterated would silently have gained keys.

Equivalence was proven, not asserted: 112 comparisons across all fourteen arms with zero mismatches, plus listcol and the nociception reconstruction on 870,172 real step rows, bit-exact against every existing copy.

scripts/analysis/ladder/_ladder.py  ·  385 lines  |  scripts/analysis/ladder/_plot.py  ·  198 lines

study facts — arm order, bin edges, run paths — and the house plotting style

_ladder holds what is true of this study rather than of stores in general: the fourteen arms in reading order, the bin edges, which run directory each arm maps to. Its loaders fail loudly and name the script to run rather than returning something empty. _plot holds the house style, including assert_labels_fit, which turns Matplotlib’s willingness to draw a label off the edge of a figure into a build failure.

4 · The figures — one script per figure, named for its number

Fifteen independent scripts. The filename carries the figure number, so Figure 8 in the report is always lad08_*.py and the page's build refuses to ship a figure whose script is missing. 5 · The page — template plus real figures plus generated tables

scripts/analysis/ladder/build_artifact.py  ·  238 lines

template + PNGs + tables → docs/experiments/active/sensor_ladder/sensor_ladder.html (8.7 MB)

The prose lives in a hand-written template; the numbers and images do not. The builder substitutes two kinds of token and fails if any is left over, so a renamed figure is an error rather than a blank panel nobody notices.

{{CODE:scripts/analysis/ladder/build_artifact.py#209-215}}

It enforces a good deal more than substitution, and all of it as hard build failures rather than warnings: every figure must name an existing generating script and appear exactly once; every caption must carry an Axes. sentence and a "How it is computed" block; every figure must declare how much data it used; and the axes sentences mirrored into the markdown report must match the template verbatim, checked before anything is written so a stale copy cannot ship.

Running it

Two commands rebuild everything downstream of the store. The first is the slow one and is only needed when the store changes; the rest take seconds.

Both sweeps take --arms to rebuild a subset, which is what makes a fourteen-arm rebuild parallelisable across nodes. The figure runner is twenty-four lines and exists only to save typing — each figure script still runs standalone:

{{CODE:scripts/analysis/ladder/run_all.py#11-18}}

It runs every figure even after one fails, then exits non-zero with the list — so one broken figure gives you the other fourteen plus a report, instead of stopping at the first traceback.

Adding a figure

  1. Check the quantity you need is already in <arm>.json. If it is, you never touch stage 2, and your edit-run loop is seconds long.
  2. Create ladNN_short_name.py with the six-line preamble above. The number must match the figure's number in the report.
  3. Open with a docstring giving the question, why it matters, and how it is computed — the published page's method block is built from it.
  4. Save through PL.finish(fig, path) so the DPI and margins match the others.
  5. Add the {{FIG:ladNN_short_name}} token to the template with an Axes. sentence, and mirror that sentence into the markdown report. The builder fails if either is missing or if the two copies differ.

If the quantity is not in the aggregates, you are adding a counter to stage 2 and re-running the sweep — minutes per arm, not seconds. That is the one expensive kind of change, and it is worth checking first.

What the refactor fixed, and what it did not

Within the ladder’s path there is now one shard loop, one set of config helpers, one population contract. The three sweeps that each carried a different subset of the same guards now share all of them, and build_arm_data.py and build_time_course.py no longer exist.

The gate, because “it should be equivalent” is not evidence

Nothing was deleted on the strength of a careful reading. Each ported sweep had to reproduce the one it replaced, checked mechanically against a snapshot taken before any code moved: integer-valued fields bit-exact, floats inside a tolerance pre-registered in the source rather than chosen after seeing a diff. Tier membership is decided by the data, so a field that failed could not be quietly reclassified into a looser tier.

The arm sweep reproduced 14 of 14 arms in both its JSON and its per-episode arrays; the time-course sweep 14 of 14; the factor sweep’s 43 arrays exactly. All fifteen figures regenerated from ported data came back byte-identical — and after the originals were deleted they were regenerated and checked again, because “the port is complete” has to mean nothing downstream noticed the swap.

The gate itself was negative-controlled before being trusted: a count off by one fails, a float nudged one part in 1011 fails, the same float nudged one part in 1014 passes, a count that acquires a fractional part is caught as a tier break, and a manifest matching nothing refuses to run rather than passing vacuously. A gate that has never rejected anything is not a gate.

What it did not fix, stated because the plan said so from the start. Two folders are deliberately frozen — scripts/analysis/figures/ and scripts/analysis/supplementary/ — because they back an earlier published study and are kept to reproduce it as published. They still carry their own copies of the config helpers, as does hiding_drivers.py. So the honest count is not one copy but two, one live and one frozen, and that was the trade rather than an oversight.

There is also a fourth store scanner, scripts/analysis/context_dependence.py, which every earlier version of the plan missed. It imports its helpers from hiding_drivers rather than copying them, so it adds no duplication, and it was out of scope here. It is the modulator study’s tool, which makes it the likeliest first client of core/ — and therefore the honest test of whether this was worth doing. If the next scanner is written against the shared scan and gets all the guards for free, the case is proven. If it is written by copying one of the existing ones again, it was not.
